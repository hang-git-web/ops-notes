## 一、进程基础

### Q1 面试官：程序和进程有什么区别？你怎么查看进程？

> **考察点**：进程概念 · `ps` vs `top` 的用途区分

**答**：

```text
程序 = 硬盘上的静态文件（比如 nginx 这个二进制文件）
进程 = 程序跑起来之后的实例（在内存里，有 PID）
一个程序可以对应多个进程。
```

| 命令 | 用途 | 关键点 |
| --- | --- | --- |
| `ps aux` | **一次性快照** | 找特定进程：`ps aux 管道符 grep nginx` |
| `top` | **实时排行** | **`P` 按 CPU 排序、`M` 按内存排序、`q` 退出** |
| `ps -ef` | 快照，能看到父进程 | 看父子关系 |
| `free -h` | 内存 | 看 `available` |

**`ps aux` 重点看三列**：

```text
USER   PID  %CPU %MEM   ...  COMMAND
       ↑    ↑    ↑
      进程号  CPU占用 内存占用
```

> **答法**：「`ps aux` 是快照，适合配合 `grep` 精确定位某个进程；`top` 是实时排行，适合看整体资源和排序找 TOP 消耗。」（把两者的**使用场景**说出来，比背参数强）

### Q2 面试官：`kill` 和 `kill -9` 有什么区别？为什么先 15 后 9？

> **考察点**：信号语义 · 优雅退出 vs 强杀
> **来源**：面经①第 4 题（完整的信号表在 `05-Q2`）

| 命令 | 信号 | 行为 |
| --- | --- | --- |
| **`kill PID`** | 15（SIGTERM） | **请进程自己体面退出**（可以保存数据、清理临时文件、关闭连接） |
| **`kill -9 PID`** | 9（SIGKILL） | **强制杀死**，进程没机会清理，**可能丢数据** |

> **标准答法**：「先 `kill`（15）让进程正常退出，如果不响应再用 `kill -9` 强杀。上来就 `-9` 可能导致数据没落盘、连接没关干净。」

**配套的一句加分**：`systemctl stop` 背后也是这个逻辑 —— 先发 SIGTERM，等 `TimeoutStopSec`（默认 90 秒），超时才补 SIGKILL。详见 `05-Q7`。

### Q3 面试官：什么是僵尸进程？怎么处理？

> **考察点**：进程回收机制 · 出现率极高

| 问题 | 答案 |
| --- | --- |
| 什么是僵尸进程 | 子进程已经结束，但**父进程没有回收它**，进程表项还留着（状态 Z） |
| 怎么处理 | **杀它的父进程**（僵尸本身已经死了，`kill` 它没用） |
| 怎么找出来 | `ps aux 管道符 grep Z` 或 `ps -eo stat,pid,comm 管道符 grep '^Z'` |

**再补一句原理（面试官爱听）**：

```text
子进程退出时会变成僵尸，等父进程调用 wait() 来"收尸"。
父进程如果一直不 wait()，僵尸就一直挂着，占用进程表项（占 PID，不占内存和 CPU）。
如果父进程也异常退出了，僵尸会被 PID 1 收养并自动回收。
```

**和孤儿进程区分（常被一起问）**：

| | 僵尸进程 | 孤儿进程 |
| --- | --- | --- |
| 谁没了 | **子进程已退出**，父进程还在但不回收 | **父进程先退出**，子进程还在跑 |
| 处理 | 杀父进程 | 不需要处理，会被 **PID 1 收养**并在退出时回收 |

### Q4 面试官：怎么把一个正在跑的前台程序放到后台？

> **考察点**：作业控制

```bash

bg                # 放到后台继续跑
jobs              # 看任务号
fg %1             # 把 1 号任务调回前台

命令 &            # 或者启动时就直接后台
nohup ./run.sh &  # 退出终端也不中断
```

## 二、服务管理（systemd）

### Q5 面试官：`systemctl start` 和 `enable` 有什么区别？`reload` 和 `restart` 呢？

> **考察点**：systemd 两件事 · **两组必考的区别**

**① start vs enable**

| 命令 | 管什么 |
| --- | --- |
| `systemctl start nginx` | **现在启动**（重启机器就没了） |
| `systemctl enable nginx` | **开机自启**（现在不一定启动） |

> **标准答法**：「这是两件独立的事：`start` 管『现在跑不跑』，`enable` 管『开机自不自动起』。部署完服务的标准做法是两个都执行：`systemctl enable --now nginx`。」

**② restart vs reload**

| 命令 | 行为 | 影响 |
| --- | --- | --- |
| `systemctl restart` | 把进程关掉重开 | **会短暂中断服务** |
| `systemctl reload` | 让运行中的进程**重读配置** | **不中断服务** |

> **标准答法**：「改完 Nginx 配置我会先 `nginx -t` 检查语法，再 `systemctl reload nginx` —— reload 只让进程重读配置、不断连接；restart 会重启进程导致短暂断服。生产上能用 reload 就用 reload。」

**最常用的命令一览**：

| 命令 | 作用 |
| --- | --- |
| `systemctl status 服务` | **看状态（最常用）** |
| `systemctl start / stop 服务` | 启动 / 停止 |
| `systemctl restart / reload 服务` | 重启 / 重载配置 |
| `systemctl enable / disable 服务` | 设置 / 取消**开机自启** |
| `journalctl -u 服务 -n 50` | 看该服务的日志 |

**`status` 输出怎么看**：

```text
Loaded: loaded (...; enabled; ...)     ← enabled = 开机自启
Active: active (running) since ...     ← active = 正在运行
```

**最健康的状态 = `enabled` + `active (running)`。**

**追问：`enable` 到底做了什么？**
本质是在 target 的 `.wants` 目录里**建了一个软链接**（比如 `/etc/systemd/system/multi-user.target.wants/nginx.service`）。所以 `enable` 是"声明我要在这个 target 下启动"，`start` 才是真正拉起进程。

### Q6 面试官：服务起不来怎么查？

> **考察点**：systemd 排障顺序 · **这是四道场景题的第 4 题**

```text
1) systemctl status 服务        —— 看状态和报错
2) journalctl -u 服务 -n 50     —— 看详细日志
3) ss -tlnp | grep 端口         —— 端口是否被占用、服务是否在监听
4) 检查配置语法（nginx -t）
5) 检查目录权限和属主（数据目录、日志目录）
6) 检查磁盘是否满（df -h）      —— ★ 最容易忽略的一条
```

**如果是「服务能起但外部访问不了」**，转向 `10-Q6` 的排查顺序（监听地址 → 防火墙 → SELinux → 实测 → 抓包）。

### Q7 面试官：怎么自己写一个 systemd 服务？服务文件放哪？

> **考察点**：systemd 单元 · 有没有自己部署过服务

| 目录 | 用途 |
| --- | --- |
| `/usr/lib/systemd/system/` | 软件包安装的（别改，升级会被覆盖） |
| **`/etc/systemd/system/`** | **管理员自建的，优先级最高** |
| `/run/systemd/system/` | 运行时生成的 |

**一个最小可用的 unit**：

```ini
[Unit]
Description=My App
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/app --config /etc/app.conf
Restart=on-failure
User=app
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload        # 改完 unit 必须重新加载
systemctl enable --now myapp   # 开机自启 + 现在启动
```

> **关键字段答法**：`[Unit]` 写 `Description`、`After`；`[Service]` 写 `Type`、`ExecStart`、`Restart`、`User`、`LimitNOFILE`；`[Install]` 写 `WantedBy`。**写完必须 `daemon-reload`**，否则 systemd 看不到。

## 三、文件描述符与 ulimit

### Q8 面试官：什么是文件描述符？报 `Too many open files` 怎么查？

> **考察点**：fd 概念 · 连接泄漏 · systemd 的坑

**先理解概念**：

```text
文件描述符（fd）= 进程打开文件/连接的"编号"
· 每打开一个文件、建立一条网络连接，都会占用一个 fd
· Linux 规定：fd 0 是标准输入、1 是标准输出、2 是标准错误
```

**排查四步（★ 会这个就够）**：

```bash
# 1) 看进程当前用了多少 fd
ls /proc/<PID>/fd | wc -l

# 2) 看这个进程的限制是多少
cat /proc/<PID>/limits | grep -i "open files"

# 3) 看具体打开的是什么（是不是连接泄漏）
lsof -p <PID> | head -20

# 4) 处理方式
#    · 数量正常但限制太小  → 调大限制
#    · 数量持续增长不回落   → 是应用没关连接（代码问题）
```

**怎么调大限制（★ 记住这个坑）**：

| 方式 | 说明 |
| --- | --- |
| 临时 | `ulimit -n 65535`（只对当前会话生效） |
| 对登录用户永久 | 改 `/etc/security/limits.conf` |
| **对 systemd 服务** | **不读 `limits.conf`**！要改 unit 文件的 `LimitNOFILE=65535`，然后 `systemctl daemon-reload && systemctl restart 服务` |

> **面试加分点**：「改完 `limits.conf` 发现服务还是报 `Too many open files`，是因为 **systemd 服务不读 `limits.conf`**，要在 unit 里设 `LimitNOFILE`。」—— 这一条能明显区分"背书的"和"跑过的"。

**ulimit 其他常用项**：

```bash
ulimit -a          # 看所有限制
ulimit -n          # 最大打开文件数（最常调）
ulimit -u          # 最大进程/线程数
ulimit -c          # core dump 文件大小（调试时放开）
```

### Q9 面试官：怎么查看一个进程打开了哪些文件、端口、线程？

> **考察点**：进程取证工具链 · 排障基本功

| 想看什么 | 命令 |
| --- | --- |
| 打开了哪些文件 / 端口 | `lsof -p PID` |
| fd 数量 | `ls /proc/PID/fd 管道符 wc -l` |
| 网络连接 | `ss -tanp 管道符 grep PID` |
| 线程 | `ps -L -p PID` 或 `top -H -p PID` |
| 进程的映射内存 | `cat /proc/PID/maps`、`pmap -x PID` |
| 进程的启动参数 | `cat /proc/PID/cmdline`、`ps -ef 管道符 grep PID` |
| 进程的工作目录 | `ls -l /proc/PID/cwd` |
| 进程的环境变量 | `cat /proc/PID/environ` |

> **加分**：「排查的时候我习惯直接进 `/proc/<PID>/`，里面几乎什么都有 —— fd、limits、maps、cmdline、cwd。文件被删了但空间没释放，就是靠 `lsof | grep deleted` 看出来的。」（把话题引到磁盘题，面试官会觉得你连贯）
