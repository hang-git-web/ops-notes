## 一、备份

### Q1 面试官：备份的 3-2-1 原则是什么？怎么验证备份可用？

> **考察点**：备份体系 · **"怎么验证"这半句才是加分点**

> **3-2-1 原则**：**3** 份数据、**2** 种介质、**1** 份异地。

**为什么需要**：不同的灾难需要不同的防线 ——

| 场景 | 本地备份能救吗 | 异地备份能救吗 |
| --- | --- | --- |
| 误删文件 | 能 | 能 |
| 硬盘损坏 | 能 | 能 |
| 服务器被盗 / 火灾 | 不能 | 能 |
| 勒索病毒 | 不能 | 能（前提是异地那份没被加密） |

**两个必答的点**：

| 问题 | 答案 |
| --- | --- |
| **备份怎么验证可用** | **定期做恢复演练** ——「备份成功 ≠ 备份可用，**必须真的恢复一次验证过**」 |
| **RAID 能代替备份吗** | **不能**。RAID 只防磁盘物理损坏，防不了误删、病毒（见 `08-Q8`） |

**你会用的备份命令（说出来就够了）**：

```bash
# 文件备份
tar -czvf /backup/www_$(date +%F).tar.gz /data/www

# 数据库备份
mysqldump -uroot -p --single-transaction --all-databases > /backup/db_$(date +%F).sql

# 同步到远端
rsync -avz /backup/ backup@192.168.1.100::backup/
```

> **加分细节**：`mysqldump` 加 **`--single-transaction`** 是为了**不锁表**（InnoDB 下拿到一致性快照）；这一条能说出来，说明你真备份过数据库。

### Q2 面试官：全量、增量、差异备份有什么区别？

> **考察点**：备份策略 · 恢复成本的权衡

> **答**：
> **① 全量备份** = 每次都完整备份（**恢复快、占空间**）；
> **② 增量备份** = 只备份**上次备份后**的变化（**占空间最小，但恢复要按链条逐个恢复**，链条断了就恢复不了）；
> **③ 差异备份** = 备份**上次全量后**的所有变化（折中：比增量占空间多一点，但恢复只需要"最后一次全量 + 最后一次差异"）。

**常见组合（说出来就是加分）**：

```text
每周日全量 + 每天增量   ← 省空间，但恢复慢、依赖链条完整
每周日全量 + 每天差异   ← 恢复快一些，空间稍多
数据库还要额外考虑：binlog（可以做"任意时间点恢复"）
```

## 二、监控

### Q3 面试官：监控应该监控哪些东西？告警为什么要分级？

> **考察点**：监控体系（三层）· 告警治理意识

**监控三层（★ 按这三层说，显得成体系）**：

```text
① 资源层：CPU、内存、磁盘使用率与 IO、网络流量、inode
② 服务层：进程存活、端口是否监听、接口响应时间、HTTP 状态码、连接数
③ 业务层：订单量、支付成功率、下单延迟、登录数   ← 最接近"用户有没有受影响"
```

**告警分级的作用**：

> **避免「所有告警都发同一个人、走同一个渠道」导致告警疲劳**。按严重程度分 P0（立即处理，打电话）/ P1（短信）/ P2（群消息）/ P3（记录），**不同级别用不同通知方式**。

> **加分的一句**：「告警的目的是让人**采取行动** —— **不能行动的告警就是噪音**，所以要定期清理无效告警、调整阈值。」

### Q4 面试官：你用过什么监控？说说架构和告警链路。

> **考察点**：结合项目 · **你有 Zabbix 实战，这题是你的加分题**

**Zabbix 架构**：

| 组件 | 作用 |
| --- | --- |
| **Server** | 负责采集与计算（触发器在这里算） |
| **Agent** | 装在被监控机上，负责取数据、执行自定义 key |
| **Proxy** | 用于大规模 / 跨网络场景（先在 Proxy 汇总再报给 Server） |
| **数据库** | 存历史数据与配置 |
| **Web 前端** | 展示与配置界面 |

**告警链路（★ 背这一条链）**：

```text
监控项采集(Item) → 触发器判断(Trigger，表达式/恢复表达式)
  → 动作(Action) → 媒介(Media：邮件/脚本/Webhook) → 收件人
```

> **结合自己的说法**：「我用 Zabbix 做过主机监控，配置了监控项采集 CPU、内存、磁盘和**自定义 key**（用 `UserParameter` 写脚本），用触发器设阈值，再通过动作把告警发到邮箱。」
> **可以主动提的排错经验（真的做过才有）**：自定义 key 不生效时，先在 server 上用 `zabbix_get -s <agentIP> -k <key>` 验证 —— **这一条是"排障第一道关口"**。

**Prometheus + Grafana（知道概念）**：

```text
Prometheus：拉取式（pull）时序数据库，指标由 exporter 暴露（node_exporter / mysqld_exporter）
Grafana   ：把 Prometheus 的数据画成看板
Alertmanager：负责告警分组、抑制、静默、路由
和 Zabbix 的区别：Zabbix 更"开箱即用、适合传统主机监控"；
                Prometheus 更适合云原生/容器（K8s），指标模型更灵活
```

## 三、容器与虚拟化

### Q5 面试官：容器和虚拟机有什么区别？容器怎么实现隔离和限制？

> **考察点**：容器原理 · **这题几乎每份运维面都会出**

| 对比 | 虚拟机 | 容器 |
| --- | --- | --- |
| **是否包含完整的操作系统** | 是（每个虚机一套内核） | **否（共享宿主内核）** |
| 启动速度 | 慢（几十秒） | **快（秒级）** |
| 资源占用 | 大（几百 MB 起） | **小（MB 级）** |
| 隔离强度 | **强**（硬件级隔离） | 相对弱（进程级隔离） |
| 代表技术 | KVM、VMware | Docker |

> **★ 一句话总结**：**「虚拟机是『虚拟出一台完整的机器』；容器是『把进程关进一个有边界的盒子』，本质是被隔离 + 被限制的普通进程。」**

**两个必然被追问的点**：

| 追问 | 答案 |
| --- | --- |
| 容器怎么实现隔离和限制 | **namespace 负责隔离**（让进程看不见别的东西），**cgroup 负责限制资源**（让进程用不了太多） |
| namespace 有哪几种 | **PID、NET、MNT、UTS、IPC、USER** 六种（对应隔离进程号、网络、挂载点、主机名、IPC、用户） |
| cgroup 限制什么 | **CPU、内存、IO、进程数（pids）** |
| 容器里 `free` 看到的是宿主机内存，为什么 | 因为容器**共享宿主内核**，`/proc/meminfo` 是全局的；**容器真正的内存限制要在 cgroup 里看**：`cat /sys/fs/cgroup/memory.max`（v2）或 `docker stats` |

**容器常用命令（知道就行）**：

```bash
docker ps -a                 # 查看所有容器（含已停止）
docker images                # 查看镜像
docker logs 容器              # 看容器日志
docker exec -it 容器 bash     # 进入容器
docker stats 容器             # 看容器的资源占用
docker inspect 容器 | grep -i oomkilled   # 看有没有被 OOM 杀过
```

### Q6 面试官：镜像分层是什么？容器里的数据怎么持久化？

> **考察点**：镜像与存储 · 有没有真用过 Docker

**镜像分层（为什么构建和分发快）**：

```text
镜像由一层层【只读层】叠加而成，Dockerfile 的每条指令生成一层；
没变的层可以复用缓存，多个容器共享同一层只有一份存储；
容器启动时在最上面加一个【可写层】。
→ 所以构建和拉取都快，而且省磁盘。
```

**数据持久化**：

```bash
# 卷（volume，Docker 管理，推荐）
docker run -v myvol:/data myimage

# 绑定宿主机目录（bind mount）
docker run -v /host/path:/container/path myimage
```

> **★ 必须说的一句**：**「不要把数据放在容器的可写层里 —— 容器一删数据就没了。要用 volume 或绑定宿主机目录。」**

**容器重启策略（了解）**：

| 策略 | 行为 |
| --- | --- |
| `no` | 默认，不重启 |
| `on-failure` | 异常退出才重启 |
| `always` | 总是重启 |
| `unless-stopped` | 除非手动停，否则重启 |

> **加分**：**「生产上我更倾向于把容器交给 systemd（或 K8s）托管，而不是只依赖 `--restart`，因为还要管开机自启、日志收集、资源限制。」**

### Q7 面试官：K8s 里 Pod、Deployment、Service 是什么关系？

> **考察点**：K8s 基础对象（简历写了 K8s 就该会）

> **答**：**Pod 是最小调度单位**（一个或多个容器）；**Deployment 管理 Pod 的副本数和滚动更新**；**Service 给一组 Pod 提供固定的访问入口和负载均衡**。都是**声明式**配置 —— 你写"期望状态"，控制器负责把实际状态拉回来。

**一句话说清 K8s 干什么**：

```text
自动部署 / 负载均衡 / 自动修复（Pod 挂了重建）/ 弹性扩缩容 /
滚动升级（不停机）/ 命名空间隔离
```

> **K8s 和 Docker 的关系（常被问）**：**Docker 是"打包和运行容器"的工具，K8s 是"管理多台机器上多个容器"的系统**。K8s 1.24 之后**移除了 dockershim**，容器运行时改成了 **containerd / CRI-O** —— 链路从「K8s → Docker → 容器」变成「**K8s → containerd → 容器**」。**这一条现在面试很爱问。**

## 四、中间件（结合你项目里的 LNMP / Redis / MySQL）

### Q8 面试官：Nginx 反向代理和负载均衡怎么配？报 502 怎么排查？

> **考察点**：Nginx · 502 排查 · 改配置的规范动作

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
server {
    location / {
        proxy_pass http://backend;
    }
}
```

> **★ 改配置的标准动作（必说）**：**「先 `nginx -t` 校验语法，再 `systemctl reload nginx`（或 `nginx -s reload`）—— 只让 master 重读配置、worker 平滑替换，**不中断连接**。生产上能用 reload 就不用 restart。」**

**502 排查顺序**：

```text
1) 看 error.log
2) 上游服务是否存活（ss -tlnp / systemctl status）
3) 上游地址端口配置对不对
4) SELinux 是否拦了（★ httpd_can_network_connect 没开 → 反向代理必 502）
5) PHP-FPM / 后端进程池是否耗尽
6) 超时参数是否合理（504 的话看 proxy_read_timeout）
```

### Q9 面试官：MySQL 慢查询怎么定位？主从复制原理是什么？

> **考察点**：数据库运维基本功

**慢查询定位**：

```text
1) 开慢查询日志：slow_query_log = ON、long_query_time = 1
2) 分析：mysqldumpslow / pt-query-digest
3) 实时看：SHOW PROCESSLIST、SHOW ENGINE INNODB STATUS
4) 看执行计划：EXPLAIN 看是否走索引、扫描行数多少
```

**主从复制原理（★ 三步）**：

```text
主库写 binlog
  → 从库的 IO 线程拉取 binlog，写入本地的 relay log
  → 从库的 SQL 线程重放 relay log
```

**主从延迟怎么查**：`SHOW SLAVE STATUS\G` 看 `Seconds_Behind_Master` 和两个 `Yes`（IO/SQL 线程）；更准确用 `pt-heartbeat`。
> **加分**：**「`Seconds_Behind_Master` 不总是准（大事务、长时间不写都会失真），所以生产上常用 `pt-heartbeat` 打心跳来测真实延迟。」**

### Q10 面试官：Redis 的 RDB 和 AOF 有什么区别？内存满了怎么办？

> **考察点**：缓存中间件 · 你项目里用过 Redis

| | RDB | AOF |
| --- | --- | --- |
| 本质 | 定时快照 | 追加命令日志 |
| 文件 | 小 | 大 |
| 恢复 | 快 | 慢 |
| 丢数据 | 可能丢最后一次快照之后的数据 | 少（`appendfsync everysec` 最多丢 1 秒） |

> **生产常两个都开**：AOF 保数据、RDB 保快速恢复和备份。

**内存满了怎么办**：

```text
1) 先确认 maxmemory 和淘汰策略（redis-cli config get maxmemory / maxmemory-policy）
2) 常见策略：
   noeviction    不淘汰，写入直接报错
   allkeys-lru   所有 key 按最近最少使用淘汰      ← 缓存场景常用
   volatile-lru  只淘汰设了过期时间的
   allkeys-lfu   按访问频率
   volatile-ttl  淘汰快过期的
```

> **Redis 的一个经典坑（说出加分）**：**Redis 官方建议 `vm.overcommit_memory=1`** —— 因为它做 RDB 时要 **fork 子进程做写时复制**，需要"超额分配"内存；如果内核不允许 overcommit，fork 可能失败或直接把 Redis 干掉。（和 `07-Q8` 的 OOM 串起来）
