# 14 项目与行为题（面试最后一关）

> **本章考什么**：技术题答完，面试官一定会问「**说说你的项目**」和「**说说你遇到过的故障**」。
> **这两题不是"聊天"，是打分项** —— 而且是你**最容易拿高分**的地方，因为你有真实项目（LNMP + Discuz、LVS/NFS/Keepalived、Docker、Zabbix、CI/CD）。
> **关键词**：项目五段式、最难故障、线上发布、学习方式、为什么选运维。

---

## 一、项目题

### Q1 面试官：介绍一个你做过的项目。（★ 必问）

> **考察点**：表达能力 · 技术深度 · **"遇到的问题"这段最能加分**
> **答题结构（五段式，★ 背下来）**：

```text
1) 背景：要解决什么问题（一句话说清，别铺陈）
2) 我的角色：我负责哪部分（一个人做就说一个人做，别吹团队）
3) 做了什么：用了哪些技术、关键步骤（重点：说清"为什么这么设计"）
4) 遇到的问题：出了什么故障、怎么排查解决的   ← ★ 这段最能加分
5) 结果：最后达成了什么效果（有数据最好：QPS、耗时、故障恢复时间）
```

**示范（用你的 LNMP + Discuz 项目套）**：

> **背景**：公司要上线一个资讯/论坛站点，需要自己搭环境并保证能扛住访问。
> **我的角色**：从环境搭建、服务部署到监控告警全流程都由我负责。
> **做了什么**：Linux 基础环境整理（关 SELinux、调文件句柄数、时间同步）→ 部署 LNMP（Nginx + MySQL + PHP-FPM）→ 部署 Discuz 并配置数据库和上传限制 → 用 Redis 做缓存 → 用 Nginx 做反向代理和负载均衡 → 加 Zabbix 监控 + 邮件告警。
> **遇到的问题**：站点上线后偶发 502，排查发现是 **SELinux 拦了 Nginx 到 PHP-FPM 的连接**（`httpd_can_network_connect` 没开），用 `ausearch -m avc` 定位、`setsebool -P` 放行后解决。
> **结果**：站点稳定运行，关键服务纳入 Zabbix 监控，故障能在 1 分钟内发现。

> **★ 讲项目时一定要"夹带"这些术语**（面试官听到就知道你真做过）：
> ```text
> nginx -t 校验 + reload 不中断发布
> systemctl enable --now（现在起 + 开机自启）
> SELinux 用 setsebool 精确放行，而不是关掉
> logrotate 防止日志写满磁盘
> 改动前备份、改完 mount -a 验证
> ```

### Q2 面试官：你在项目里做过哪些优化？（如果简历写了"优化"）

> **考察点**：架构思维 · 能不能说出"为什么要优化"
> **答题要点**：**每一个优化都要说"原来有什么问题 → 改了什么 → 解决了什么"**，不能说"我加了个 Redis"就完了。

**常见的六类优化（挑 2~3 个说）**：

| 优化 | 原来什么问题 | 改了什么 |
| --- | --- | --- |
| **加缓存** | 每次请求都查数据库，数据库压力大 | 加 Redis 缓存热点数据，降低 DB QPS |
| **读写分离 / 主从** | 单库读写都在一台机器 | MySQL 主从，写主读从 |
| **负载均衡** | 单台 Web 挂了站点就没了 | Nginx / LVS 做多台 Web 的负载均衡 + Keepalived 高可用 |
| **静态资源分离 / CDN** | 图片 CSS 也压在后端 | Nginx 直接处理静态文件、开 `sendfile`（零拷贝） |
| **连接复用** | 大量短连接导致 TIME_WAIT 堆积 | 开长连接 / 连接池（见 `10-Q8`） |
| **可观测性** | 出问题靠用户报障才发现 | 加 Zabbix/Prometheus 监控 + 分级告警 |

> **一句话总结（很加分）**：**「优化的顺序一般是：先加监控能看见问题 → 再解决最影响用户的瓶颈 → 然后做冗余（高可用）→ 最后才是性能和成本的细调。」**

## 二、故障题

### Q3 面试官：你排查过最难的故障是什么？怎么定位的？（★ 必问）

> **考察点**：排查思路 · **面试官听的是"思路"，不是"结论"**
> **★ 答题结构（四件事，缺一不可）**：

```text
1) 现象：谁在什么时候报了什么错（越具体越好）
2) 排查过程：怎么分层缩小范围、用了哪些命令、每一步的依据是什么
3) 根因：最后定位到什么
4) 复盘：加了什么监控 / 规范，避免再犯
```

**示范（用真实的坑）**：

> **现象**：一台服务器告警磁盘使用率 100%，但 `du` 逐层查下来加起来只有 20%。
> **排查**：先用 `df -h` 确认是 `/` 满 → `du -sh /* | sort -h` 逐层找，加起来对不上 → 想到两个特例：查 `df -i` 发现 **inode 正常**；再 `lsof | grep deleted`，发现是 **一个日志文件被删了但进程还持有句柄**，空间没释放。
> **根因**：日志量大，运维用 `rm` 删了日志文件，但服务没重启 / 没发信号重开日志，所以 inode 一直被占着。
> **复盘**：① 删日志改成 `> app.log` 清空或用 logrotate；② 配 logrotate 自动轮转 + postrotate 发信号；③ 磁盘使用率和 inode 都纳入监控。

> **加分收尾**：「这件事让我养成了两个习惯：**删日志用清空而不是 rm**，以及**改 fstab / 改 sshd 这类高风险配置前先备份、改完先验证再退出**。」

**可以准备的"备用故障"清单**（挑一个你最熟的）：

| 故障 | 一句话根因 |
| --- | --- |
| Too many open files | 应用连接没关（fd 泄漏）或 `LimitNOFILE` 太小 |
| CLOSE_WAIT 堆积 | 应用没调用 `close()`（代码问题） |
| 服务起不来 | 端口占用 / 配置语法错 / 权限不对 / 磁盘满 |
| 502 Bad Gateway | 上游挂了 / SELinux 拦了 / FPM 池耗尽 |
| 内存告警但没 OOM | `buff/cache` 是缓存，看 `available` 和 `si/so` |
| load 高 CPU 低 | 卡在磁盘 IO（D 状态进程） |
| 磁盘满且 `df`/`du` 对不上 | inode 用尽 或 deleted file 未释放 |

### Q4 面试官：线上发布出问题了，你怎么办？

> **考察点**：应急意识 · **"先止损"的顺序感很重要**

```text
1) 先止损：回滚 / 切流量 / 限流 / 摘掉故障节点   ← ★ 先恢复业务，别急着查根因
2) 再定位：对比发布前后的监控、日志、变更记录差异
3) 修复并验证：改完再看监控和日志确认恢复
4) 事后：补上"能提前发现这个问题"的监控和发布检查项
```

> **★ 一句加分的话**：**「我的原则是——先让业务恢复，再找原因；同时**不能回滚的变更不上生产**。」**

**发布前的检查项（说出来显得规范）**：

```text
备份 / 快照 → 低峰期执行 → 灰度或分批 → 观察监控和日志 → 有问题按预案回滚 → 记录变更
```

## 三、行为题

### Q5 面试官：遇到不会的问题 / 没做过的任务，你怎么处理？

> **考察点**：学习能力 · 会不会瞎干

> **答**：「我会分三步：① 先**自己查** —— 官方文档、日志、报错信息；② 查不到就**缩小范围做实验**，在测试机上复现；③ 还不行就**带着"我已经排查到哪一步、我的猜测是什么"去问人**，而不是空手问。
> 关键是我习惯**把踩过的坑写成笔记**（比如这套笔记就是这么来的），下次遇到就能直接查。」

---

### Q6 面试官：你平时怎么学习、怎么保持技术更新？

> **考察点**：学习习惯 · 有没有自驱力

> **答**：「① **结合项目做实验环境** —— 学一个新东西就在虚拟机/容器里跑一遍；② 看**官方文档**，而不是只搜二手教程；③ **把踩的坑沉淀成笔记**，就像我这份运维笔记库，分五个阶段；④ 关注社区和线上的**故障复盘案例**，看别人怎么定位问题。」

---

### Q7 面试官：为什么选择运维这个岗位？

> **考察点**：动机是否真实 · **别背模板**

> **答（用一个例子支撑，比空谈好）**：「我比较喜欢**把系统跑稳**和**排查问题**这个过程 —— 有一次线上磁盘告警，我一路查到是 inode 用尽，那种"从现象追到根因"的感觉很吸引我。另外我也喜欢**用自动化减少重复劳动**，比如把日常巡检写成脚本挂到定时任务。所以运维对我来说既是兴趣，也是能长期积累的方向。」

---

### Q8 面试官：你的缺点是什么 / 你觉得运维最重要的是什么？

> **考察点**：自我认知 · 职业观

**缺点（选一个真实但无害的 + 说明在改）**：
> 「经验上我相对欠缺的是**大规模集群的实战**，目前接触的机器数量有限。所以我在用 K8s、监控这些方向补 —— 已经自己搭了 kind 集群做过实验。」

**运维最重要的是什么（★ 这题答好了很加分）**：
> 「我认为是**责任心和规范意识**。运维的动作经常是不可逆的 —— `rm -rf`、`mkfs`、改 fstab，一个手滑就可能让业务挂掉。
> 所以我的习惯是：**动手前先备份、先确认目标、改完先验证**；能回滚的变更才上生产；同时把**监控和告警**做在前面，**不要等用户报障才知道出问题**。」

## 四、面试收尾

### Q9 面试官：你有什么想问我的？

> **考察点**：有没有认真准备 · **别说"没有"**

**推荐问的（按加分排序）**：

```text
1) 这个岗位日常最常处理的故障类型是什么？团队现在最缺的能力是哪块？
2) 团队的监控体系是怎么搭的？（Zabbix / Prometheus / 云监控）
3) 团队现在自动化到什么程度？有没有用 K8s / CI-CD？
4) 新人入职前建议先补哪块知识？
```

**不建议问**：「加不加班」「几点下班」「能不能远程」（这些可以留到 offer 阶段，面试时问会显得动机不对）。

## 五、本章追问链

```text
讲项目        →  为什么这么设计？（讲取舍）
              →  遇到什么故障？（讲排查过程）
              →  如果流量翻 10 倍怎么办？（扩容 / 缓存 / 负载均衡 / 读写分离）
              →  这套环境你自己搭的吗？（诚实，别吹）
讲故障        →  怎么定位的？（分层缩小范围）
              →  根因是什么？（说清机制）
              →  怎么避免再犯？（监控 + 规范）
线上发布      →  先做什么？（止损优先）
              →  不能回滚怎么办？（所以不能回滚的变更不上生产）
行为题        →  遇到不会的怎么办？（查文档 → 实验复现 → 带方案问人）
              →  为什么选运维？（用真实例子支撑）
```
