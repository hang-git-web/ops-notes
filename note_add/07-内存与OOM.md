# 07 内存、虚拟内存与 OOM

> **本章考什么**：从「`free` 怎么读」一直到「内核这一层发生了什么」。
> **关键词**：free 各字段、available vs buff/cache、RSS/VSZ/SHR、缺页中断、mmap、swap、OOM、内存泄漏。
> **来源**：面经①第 10、14 题（**原稿只有现象、没有机制，这章补齐了内核那一层**）。

---

## 一、内存怎么看（先破除最大的一个误区）

### Q1 面试官：`free` 里 `buff/cache` 占了 8G，是不是内存不足？

> **考察点**：内存判定标准 · page cache 的本质
> **这是内存题的第一道关，答错直接掉印象分。**

```bash
free -h
              total        used        free      shared  buff/cache   available
Mem:           15Gi       6.2Gi       1.1Gi       412Mi       8.4Gi       8.9Gi
Swap:         4.0Gi          0B       4.0Gi
```

**三个关键认知（★ 面试常考）**：

| 认知 | 说明 |
| --- | --- |
| **1 `buff/cache` 大 ≠ 内存不足** | 这是**缓存**（Linux 拿空闲内存缓存文件数据加速），应用需要时会自动回收 |
| **2 判断内存够不够看 `available`** | **不是看 `free`，也不是看 `used`** |
| **3 真正缺内存的信号是 `si/so`** | `vmstat 1` 里持续非 0（说明在换页）才说明内存压力大 |

> **标准答法（背这一段）**：
> 「`free` 里 `buff/cache` 占了很多是正常的，那是**缓存**；判断内存是否充足要看 **`available`** —— 它才是应用真正还能拿到的内存。如果 `vmstat` 里 `si/so` 持续不为 0，才说明内存真的紧张。」

**为什么 `buff/cache` 是可回收的**：内核把读过的文件页缓存在内存里（page cache）；应用要内存时，**没被修改过的缓存页可以直接丢掉**（需要时再从磁盘读回来），所以它不算是"被占用"。

**`free` 各字段的含义**：

| 字段 | 含义 |
| --- | --- |
| `total` | 物理内存总量 |
| `used` | 已用（= total − free − buff/cache） |
| `free` | **完全没用的空闲**（很小是正常的） |
| `shared` | tmpfs / 共享内存占用 |
| `buff/cache` | 块设备缓冲 + 文件页缓存（**可回收**） |
| **`available`** | **应用真正还能拿到的内存（看这个）** |

**追问：能不能手动释放 cache？**
**能但生产慎用**：`echo 3 > /proc/sys/vm/drop_caches`。它是缓存不是泄漏；释放后系统还要重新读盘，**性能反而变差**。

### Q2 面试官：内存不够会有什么现象？

> **考察点**：现象识别 · OOM 的入口

```text
· 系统变慢（频繁换页到 swap，wa 变高）
· 进程被 OOM Killer 杀掉 → dmesg | grep -i oom 能查到
· 容器里的进程被杀 → 状态显示 OOMKilled
· 新进程 fork 失败（Cannot allocate memory）
· 日志里出现 "Out of memory: Killed process ..."
```

### Q3 面试官：怎么看一个进程到底占了多少内存？VIRT / RES 哪个有意义？

> **考察点**：RSS vs VSZ · 排查内存要盯哪个

| 指标 | 含义 | 注意 |
| --- | --- | --- |
| **VIRT / VSZ** | 虚拟地址空间总量 | **几乎没用**：包含未分配、共享库、映射的文件 |
| **RES / RSS** | **实际驻留在物理内存里的量** | **排查内存要盯这个**（不含被换出的部分） |
| **SHR** | 其中可共享的部分（共享库、共享内存） | 不能简单从 RSS 里减去 |

> **一句话**：**「看内存占用看 RSS，不看 VIRT；RSS 持续只涨不落才是可疑的泄漏。」**

```bash
ps aux --sort=-%mem | head          # 按内存排序找进程
top                                 # 按 M 排序
cat /proc/<PID>/smaps_rollup        # 进程内存构成：Rss / Pss / Anonymous / Shared
```

## 二、虚拟内存与缺页中断（机制层）

### Q4 面试官：什么是虚拟内存？页和页表是什么？

> **考察点**：地址空间抽象 · 隔离与换页的基础
> **来源**：面经①第 14 题的上半部分

```text
每个进程看到的是"独立、连续的虚拟地址空间"（32 位 4G；64 位巨大）
  ↓ 通过页表（page table）按"页"映射（x86 默认 4KB 一页）
物理内存（内存条上的真实字节）
  ↓ 页表项命中率靠 TLB 缓存（TLB 未命中 = 需要多级页表查询）
```

| 概念 | 一句话 |
| --- | --- |
| **虚拟内存** | 进程看到的地址空间；提供隔离、连续地址、可换出到 swap、可共享 |
| **物理内存** | 真正装在机器上的内存条 |
| **页（page）** | 内存管理的最小单位，通常 4KB |
| **页表 / TLB** | 虚拟地址 → 物理地址的映射表 / 它的高速缓存 |
| **匿名页** | 没有对应文件的页（堆、栈、malloc 出来的内存）→ **回收时只能写 swap** |
| **文件页** | 对应磁盘文件的页（程序、数据、page cache）→ **可直接丢弃再读回** |

> **为什么需要虚拟内存（说这三条就够）**：① **隔离**：进程 A 碰不到进程 B 的内存；② **连续假象**：不必要求物理内存连续，解决碎片；③ **超量使用**：可以换出到 swap、可以按需加载。

---

### Q5 面试官：缺页中断是什么？major 和 minor 有什么区别？

> **考察点**：按需分页 · 内存访问的开销
> **来源**：面经①第 14 题

**过程（按这个顺序说）**：

```text
1) 进程访问一个虚拟地址
2) CPU 查页表：发现这一页"不在物理内存"（页表项无效）
3) 触发缺页异常（page fault），陷入内核
4) 内核判断属于哪种情况：
   · 从来没分配过 → 分配一个物理页（可能填零）
   · 页在 page cache / 已在内存但没建立映射 → 建立映射
   · 页被换出到 swap 或存在文件里 → 发起磁盘 IO 读回来
5) 更新页表（并刷新 TLB）
6) 返回用户态，重新执行刚才那条指令 —— 这次就成功了
```

> **一句话**：**「缺页中断不是错误，而是内存按需加载的机制；访问的页不在内存里，内核把它准备好再让指令重跑一次。」**

**两种缺页（★ 关键区分）**：

| 类型 | 定义 | 代价 | 典型场景 |
| --- | --- | --- | --- |
| **minor（次要）缺页** | 页其实**已经在物理内存里**，只是还没建立映射 | 小（不涉及磁盘） | 首次访问 malloc 的堆、`mmap` 建立映射、写时复制 COW |
| **major（主要）缺页** | 页**不在内存，必须读磁盘**（swap 或文件） | **大（一次磁盘 IO）** | 进程被换出后又被唤醒、首次读大文件 |

```bash
# 怎么看缺页
/usr/bin/time -v ./程序        # 输出 minor/major page faults
ps -o pid,min_flt,maj_flt,cmd -p <PID>
cat /proc/vmstat | grep -E 'pgfault|pgmajfault'
sar -B 1 5                    # fault/s、majflt/s
```

> **性能经验**：**major fault 持续很高 = 在疯狂读磁盘 / swap，系统会明显变卡**（这时候 `si/so`、`wa` 一般也高）。

---

### Q6 面试官：内存映射（mmap）是什么？有什么用？

> **考察点**：mmap 机制 · 和 page cache、共享内存的联系
> **来源**：面经①第 14 题

```text
mmap = 把一个文件（或一块匿名内存）映射到进程的虚拟地址空间。
之后进程"读写内存"就等于"读写文件"，不用 read/write 系统调用搬运。
```

| 类型 | 说明 | 典型用途 |
| --- | --- | --- |
| **文件映射** | 映射一个文件，页来自 **page cache** | 加载动态库（`libc.so`）、大文件随机读写 |
| **匿名映射** | 不关联文件，只能放内存 / swap | `malloc` 的大块内存、共享内存 |
| **私有（MAP_PRIVATE）** | 写时复制（COW），改动不回写文件 | 加载程序段 |
| **共享（MAP_SHARED）** | 多个进程看到同一份改动 | **进程间共享内存（IPC）** |

**为什么要用它（说这三点就够了）**：

```text
1) 快：少一次用户态 ↔ 内核态的数据拷贝（对大文件尤其明显）
2) 共享：多个进程映射同一个文件 / 同一段匿名内存，天然共享
3) 按需加载：只有真正访问到的页才读进来（配合缺页中断）
```

```bash
# 怎么看一个进程映射了什么
cat /proc/<PID>/maps      # 每一行的区间、权限、来源文件
pmap -x <PID>             # 更可读，带 RSS / Dirty
cat /proc/<PID>/smaps_rollup   # 汇总：Rss / Pss / Anonymous / Shared
```

> **联系前面**：`free` 里的 `buff/cache` 很大一部分就是这些文件映射带来的 **page cache** —— **它是缓存，不是内存不够**（Q1 已经讲过）。这个"把两题串起来"的能力，面试官很吃。

## 三、swap 与 OOM

### Q7 面试官：swap 是什么？什么情况会用到它？

> **考察点**：换页机制 · 判断内存压力的指标
> **来源**：面经①第 10 题

```text
swap = 磁盘/SSD 上划出来的一块空间，作为内存的后备。
内存紧张时，内核会先回收"文件页"（直接丢掉，需要时再读回来），
再回收不动就只好把"匿名页"写到 swap（换出），等进程再用到时再读回来（major fault）。
```

| 概念 | 说明 |
| --- | --- |
| `kswapd` | 后台回收线程，空闲内存低于水位时开始回收 |
| **直接回收** | 内存实在不够时，进程自己的分配请求被迫去回收 → **卡顿** |
| `vm.swappiness` | 0~100，越大越倾向于换出匿名页（默认 60；**数据库常调到 1~10**） |
| `si / so` | `vmstat` 里的换入 / 换出速率，**持续非 0 = 内存真的紧张** |

```bash
free -h ; swapon --show ; cat /proc/swaps
vmstat 1 5                 # 看 si/so
sysctl vm.swappiness       # 看当前值
```

> **什么情况下"会用 swap"**：① 内存压力大（`available` 低于水位）；② `swappiness` 偏高；③ 应用有大量"长时间不访问的匿名页"；④ 内存限制（容器 / cgroup）被触发。
> **注意**：**swap 用起来不是"故障"，但 swap 频繁读写就是性能灾难**（机械盘随机 IO 比内存慢几万倍）。很多数据库 / 中间件要求关掉 swap 或调到很低。

**追问：生产环境要不要开 swap？**

> 普通服务器建议留一点（内存的 1~2 倍或按需，比如 4~8G）当**缓冲**，防止一次内存尖峰直接触发 OOM；但**数据库 / 中间件（MySQL、Redis）和 K8s 节点**一般要求关掉或把 `vm.swappiness` 调到 1~10，避免换页导致**延迟抖动**。

### Q8 面试官：OOM 是什么？什么会导致 OOM？

> **考察点**：OOM Killer 机制 · 能不能分门别类地说原因
> **来源**：面经①第 10 题

**是什么**：

```text
物理内存 + swap 都回收不出空间，新的内存申请无法满足
  → 内核的 OOM Killer 介入，按 oom_score 挑一个进程杀掉，回收它的内存
  → 目的是保住系统本身不崩
```

**什么会导致 OOM（★ 按类别说，显得有条理）**：

| 类别 | 具体原因 |
| --- | --- |
| **应用层** | ① **内存泄漏**（只申请不释放）② 并发/流量激增，瞬时申请太多 ③ 一次性加载大文件、大查询结果集 ④ JVM/进程堆参数设得比物理内存还大（`-Xmx` 超配） |
| **内核参数** | ⑤ **overcommit**（允许超量分配，`vm.overcommit_memory=1` 时更容易 OOM）⑥ `swappiness` / 水位设置不当，缓存回收不及时 |
| **资源规划** | ⑦ swap 太小或没开，没有缓冲 ⑧ 多个服务挤在一台机器上，总量超过物理内存 ⑨ 容器 / cgroup 内存 limit 设太小（容器里报 `OOMKilled`） |
| **不可回收** | ⑩ 内核页、共享内存段、锁定内存（`mlock`）太多，page cache 回收不动 |

**OOM Killer 怎么挑人**：

```text
评分基础 = 该进程占用的内存（RSS）越大分越高
      × 调整值（oom_score_adj，-1000 ~ 1000）
      并受"是否为 root 进程"等规则影响（root 进程有保护，评分打折）

查看：cat /proc/<PID>/oom_score 、/proc/<PID>/oom_score_adj
保护：echo -1000 > /proc/<PID>/oom_score_adj    （让它几乎不会被杀）
```

**出了 OOM 怎么查**：

```bash
dmesg -T | grep -i -E 'out of memory|killed process'
journalctl -k | grep -i oom
/var/log/messages          # CentOS 系；Ubuntu 在 /var/log/syslog
docker inspect <容器> | grep -i oomkilled       # 容器
```

典型日志：

```text
Out of memory: Killed process 12345 (java) total-vm:..., anon-rss:..., oom_score_adj:0
```

**怎么防（四步）**：

```text
1) 定位：找到被杀进程 + 它为什么吃这么多内存（泄漏？参数太大？）
2) 限制：systemd 的 MemoryMax / 容器 memory limit / JVM -Xmx / 应用连接池上限
3) 兜底：加内存、适度加 swap、调 overcommit 与 swappiness
4) 监控：把 available、si/so、OOM 日志都纳入告警
```

> **Redis 的一个经典坑（说出加分）**：Redis 官方建议 `vm.overcommit_memory=1`，否则在 **fork 做 RDB 持久化**时可能因为"内存超量分配被拒绝"而失败，或直接触发 OOM 把 Redis 干掉。

## 四、内存泄漏排查

### Q9 面试官：内存泄漏怎么排查？

> **考察点**：先区分"高"和"泄漏" · 工具链 · 运维侧的兜底
> **来源**：面经①第 14 题

**第一步：先分清"内存高"和"内存泄漏"**：

| 现象 | 是不是泄漏 |
| --- | --- |
| `buff/cache` 很大、`available` 还够 | 不是，正常缓存 |
| 进程 RSS 稳定在高位、重启后回落 | 可能是配置太大 |
| **进程 RSS 单调上升、不回落、重启才恢复** | **是，典型的泄漏** |

**第二步：排查流程（★ 这套背下来）**：

```text
1) 定位到进程：free -h / top 按 M 排序、ps aux --sort=-%mem | head
2) 看趋势（关键）：定时采样 RSS，画出来是不是只涨不落
   while true; do ps -o rss= -p <PID>; sleep 60; done
3) 看内存构成：pmap -x <PID> / cat /proc/<PID>/smaps_rollup
   （Anonymous 涨 = 堆内存涨；映射的库/文件涨是另一回事）
4) 交给应用侧工具（按语言）
   · Java：jmap -histo:live / jmap -dump + MAT、jstat -gcutil 看老年代
   · C/C++：valgrind --leak-check、heaptrack
   · Go：pprof
   · 通用：strace -f -e trace=brk,mmap 看不释放的申请
5) 运维侧兜底：加监控告警、设置 MemoryMax 限制、
   极端情况先 gcore 保留现场再重启保业务
```

> **一句话总结**：**「先用 `top`/`ps` 找到进程，看 RSS 是不是只涨不落，再用 `pmap`/`smaps` 看是哪一类内存涨，最后交给应用侧工具（Java 用 jmap、C 用 valgrind）定位到代码；运维能做的是监控、限制和保住现场。」**
