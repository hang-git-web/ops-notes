## 一、top 输出的五段结构（先知道哪一段是什么）

```text
top - 10:24:31 up 12 days,  3:15,  2 users,  load average: 0.52, 0.58, 0.59
Tasks: 231 total,   1 running, 229 sleeping,   1 stopped,   0 zombie
%Cpu(s):  3.2 us,  1.5 sy,  0.0 ni, 94.0 id,  1.2 wa,  0.0 hi,  0.1 si,  0.0 st
MiB Mem :  15884.0 total,   1120.5 free,   6234.2 used,   8529.3 buff/cache
MiB Swap:   4096.0 total,   4096.0 free,      0.0 used.   8890.1 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1234 root      20   0  2130000 450000  12000 S  45.3   2.8  120:31.22 java
```

| 行 | 看什么 |
| --- | --- |
| **第一行** | 时间、开机多久、**load average（1/5/15 分钟平均负载）** |
| 第二行 | 进程总数 / 运行中 / 睡眠 / 停止 / **僵尸** |
| **第三行** | **CPU 8 个字段（本篇重点）** |
| 第四行 | 物理内存：total / free / used / **buff/cache** / **available** |
| 第五行 | swap 使用情况 |
| 表头 | `%CPU` `%MEM` `RES`（实际内存）`TIME+`（累计 CPU 时间）`S`（进程状态）|

## 二、`%Cpu(s)` 八个字段（★ 面经第 5 题，逐个背）

| 字段 | 含义 | 高的时候说明什么 | 怎么查下去 |
| --- | --- | --- | --- |
| **us** | 用户态 CPU 时间（普通用户进程） | 应用自己在算：死循环、复杂计算、正则、频繁 GC | `top -H -p <pid>` 找线程；Java `jstack` |
| **sy** | 内核态 CPU 时间（执行内核代码） | **系统调用/上下文切换太频繁**：IO 切换、进程/线程太多、锁竞争 | `vmstat 1` 看 `cs`；`pidstat -w`；`strace -c` |
| **ni** | 低优先级（nice 值）进程占的 CPU | 有人调低了优先级在跑重活（和 us 本质相同，单独统计便于区分）| `ps -eo pid,ni,pcpu,cmd --sort=-ni` |
| **id** | 空闲 | 高就是 CPU 闲（**`100 - id` ≈ 总使用率**）| — |
| **wa** | 等 IO 的时间（**CPU 空闲但有 IO 未完成**）| **磁盘/网络存储是瓶颈**，不是 CPU 忙 | `iostat -x 1` 看 `%util`、`await` |
| **hi** | 硬中断（硬件中断处理） | **网卡收包太猛**（大量小包、DDoS）、磁盘中断 | `/proc/interrupts`；`mpstat -P ALL 1` |
| **si** | 软中断（内核协议栈处理） | **网络流量大**（大量连接/高吞吐），常和 hi 一起高 | `softnet_stat`；`ksoftirqd` 线程 CPU |
| **st** | 被宿主机"偷走"的时间 | **虚拟机/云主机超卖**：你想跑但宿主机没给你 CPU | 联系云厂商；查宿主机负载 |

> **记忆法**：**"us 是应用在算，sy 是内核在忙，wa 是在等盘，ni 是低优先级，hi/si 是网卡，st 是别人抢走了，id 是闲着。"**

### 2.1 一个必记的判断逻辑

```text
CPU 真忙：us / sy 高，id 低              → 找进程、找线程、看是不是计算型
IO 瓶颈：wa 高，us 不高                  → 加 CPU 没用，要看磁盘（iostat）
网络瓶颈：hi / si 高                     → 看网卡、看连接数、看是不是被攻击
超卖：st 高                              → 云主机/虚拟机，宿主机资源不够
ni 高                                    → 有人在 nice 调低优先级跑批处理
```

### 2.2 hi / si 一句话补充（可能被追问）

```text
网卡收到包 → 触发硬中断（hi）→ 内核把它标记为"待处理的软中断" → 由 ksoftirqd 或中断返回路径处理（si）
所以"突发流量/大量小包"会让 hi、si 一起升高；看 /proc/softnet_stat 和 /proc/interrupts 能定位到哪张网卡。
多队列网卡（RSS/RPS）+ 中断亲和性可以把这个压力分摊到多个核。
```

## 三、top 的常用交互键（面试可能让你现场说） 

| 按键 | 作用 |
| --- | --- |
| `P` | **按 CPU 排序**（默认） |
| `M` | **按内存排序** |
| `T` | 按累计 CPU 时间排序 |
| `1` | **展开每个核的使用率**（多核机器排查必用）|
| `H` | 显示线程（等价于 `top -H`）|
| `c` | 显示完整命令行（看到启动参数）|
| `k` | 在界面里杀进程 |
| `r` | renice（调整优先级）|
| `z` | 彩色高亮 |
| `q` | 退出 |
| `W` | 把当前配置写成 `~/.toprc` |

```bash
top -b -n 1 | head -20          # 一次性输出（脚本/日志里常用）
top -H -p 1234                  # ★ 看某个进程内部"哪个线程"在吃 CPU
top -p $(pgrep -d, nginx)       # 只看某些进程
```

## 四、load average 怎么读（★ 一定会被追问）

```text
load average = 过去 1 / 5 / 15 分钟，平均有多少个"任务"在排队。
任务 = 正在跑 + 等 CPU 的可运行进程 + 不可中断睡眠（D 状态，等 IO）的进程
判断标准：和"核数"比，不是和 100% 比
  load ≈ 核数        → 差不多跑满
  load > 核数        → 开始排队，响应变慢
  load >> 核数       → 严重排队（经验值：超过核数 2 倍要处理）
```

```bash
nproc                       # 看几个核（★ 不要凭感觉）
uptime                      # 看 1/5/15 分钟负载
cat /proc/loadavg           # 负载 + 当前可运行数/总进程数
vmstat 1 5                  # r = 运行队列，b = 阻塞（D 状态）进程数
```

### 4.1 "load 很高但 CPU 使用率很低"（★ 高频追问）

| 原因 | 怎么确认 |
| --- | --- |
| **磁盘/网络 IO 卡住**，大量进程处于 D 状态 | `vmstat` 的 `b` 很大、`wa` 高、`iostat` 的 `%util` 高 |
| **内存不足在换页** | `vmstat` 的 `si/so` 非 0 |
| **进程被 cgroup 限流**（容器 CPU quota 用满） | `cat /sys/fs/cgroup/.../cpu.stat`、容器被 throttle |
| **宿主机超卖**（虚拟机 st 高） | `top` 里的 `st` |

> **答法**：**"load 统计的是运行队列 + D 状态的进程，所以 IO 卡住、换页、被限流都会让 load 升高但 CPU 不高。这时候要看 `vmstat` 的 `r/b/wa/si/so` 去区分到底是 CPU 排队还是 IO 排队。"**

## 五、上下文切换（和 sy 高是配套的）

```bash
vmstat 1 5              # cs 列 = 每秒上下文切换次数
pidstat -w 1            # 每个进程的自愿/非自愿切换
pidstat -w -t -p <PID>  # 线程级
```

| 概念 | 说明 |
| --- | --- |
| 自愿切换 | 进程主动让出 CPU（等 IO、sleep） |
| **非自愿切换** | 时间片用完被抢占 / 被更高优先级抢占 → **多了说明线程太多或锁竞争** |
| 经验值 | `cs` 上万且 `sy` 高，基本可以判断是"系统调用/切换开销大" |

## 六、场景题加练：四核 CPU 从 20% 飙到 100%（面经第 15 题）

### 6.1 标准排查流程（照着说）

```text
① 先确认现象，别急着动手
   uptime（看 1/5/15 分钟负载趋势：是刚飙还是持续高）、top 看整体字段
   —— 同时想一句："是不是刚发布、是不是有定时任务、是不是流量变了"

② 定位到"哪个进程"
   top -b -n 1 | head -20            # 一次性看排行
   ps aux --sort=-%cpu | head        # 按 CPU 排序

③ 定位到"哪个线程"（四核机器上，单线程死循环只能吃 25%）
   top -H -p <PID>                   # 看线程级 CPU
   ps -L -p <PID> -o pid,tid,pcpu,comm --sort=-pcpu | head

④ 用第三行字段判断"是哪一类 CPU 消耗"
   us 高 → 应用自身计算（代码 bug、GC、正则回溯、死循环）
   sy 高 → 频繁系统调用/上下文切换（线程太多、锁竞争、IO 频繁）
   wa 高 → 其实是等磁盘，属于 IO 问题（去 iostat）
   hi/si 高 → 网络（大流量、小包、被攻击）
   st 高 → 宿主机超卖（云主机），你自己无能为力

⑤ 再深入
   通用：strace -p <PID> -c（看系统调用占比）、perf top -p <PID>
   Java：jstack <PID> 看线程栈、jstat -gcutil <PID> 1s 看 GC
   PHP/Python：看慢日志、用 py-spy
   如果是 IO：iostat -x 1 看哪块盘的 %util / await

⑥ 处理与验证
   业务高峰 → 扩容/限流；代码问题 → 回滚或修；异常进程（挖矿/失控）→ 先留证据再 kill
   处理完再看一遍 top/uptime 确认回落到正常；最后记工单/复盘
```

### 6.2 一条命令快速取证（可以背下来）

```bash
(date; uptime; echo; top -b -n 1 | head -25; echo; \
 vmstat 1 5; echo; iostat -x 1 3; echo; \
 ps aux --sort=-%cpu | head -10) | tee /tmp/cpu_check_$(date +%F_%H%M).txt
```

> **面试加分**：**"我会先留一份现场（top/vmstat/iostat 输出），再动手，避免处理完查不到原因；同时对比 1/5/15 分钟负载和监控历史，判断是突发还是持续增长。"**

### 6.3 常见的"真凶"清单（说出来立刻显得有经验）

```text
· 死循环 / 代码 bug（us 高，负载随时间持续）
· JVM 频繁 Full GC（us 高 + 内存曲线锯齿；jstat 能看到）
· 定时任务/备份/日志压缩撞在一起（每天固定时间点飙升）
· 被压测或被扫描/被挖矿（外部连接暴增，hi/si 高，进程名可疑）
· 数据库慢查询（sy/wa 高，磁盘也忙）
· 线程/连接数配置过大导致上下文切换暴涨（sy 高，cs 上万）
```

## 七、面试答法模板

**Q：top 里 CPU 这些字段分别是什么？**
A：us 是用户态、sy 是内核态、ni 是低优先级进程、id 是空闲、wa 是等 IO、hi 是硬中断、si 是软中断、st 是被宿主机偷走的时间。**判断时：us 高是应用在算，sy 高是系统调用和切换多，wa 高其实是磁盘的问题，hi/si 高看网络，st 高说明宿主机超卖。**

**Q：四核 CPU 突然 100%，你怎么办？**
A：先说思路——**先确认现象，再定位进程，再定位线程，再判断是哪类 CPU 消耗，最后处理并验证**。具体：`uptime` 看负载趋势、`top` 看 8 个字段，`ps aux --sort=-%cpu`/`top -b -n 1` 找到进程，`top -H -p` 找到线程；如果是 us 高就用 jstack/perf 看应用，sy 高看上下文切换和系统调用，wa 高就去 iostat 查磁盘。处理上高峰扩容、bug 回滚、异常进程清理，处理前后各留一份现场。
