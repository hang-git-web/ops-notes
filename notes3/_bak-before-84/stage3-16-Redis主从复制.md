# Redis 的主从复制

## 主从复制原理

这一节把"复制到底是怎么发生的"讲清楚，理解它之后，后面各条配置的作用就好理解了。

### 整体机制

- 主从复制是**异步**的、**单向**的：数据从主节点流向从节点，写操作只能在主节点上做，从节点默认只读。
- "异步"的意思是主节点把写命令发给从节点后并不等待确认，就直接回复客户端。好处是不影响主节点的性能，代价是主节点突然宕机时，最后一批还没传过去的写入会丢失。
- 主从复制本身**不包含自动故障切换**。它只解决数据冗余和读扩展，要做到主节点挂了自动顶上，还需要 Sentinel（哨兵）或 Redis Cluster。

### 三个阶段

一次完整的主从关系建立，会经历三件事：

1. 建立连接、协商同步方式
2. 全量同步（第一次连接时，或无法做增量同步时）
3. 命令传播（之后持续进行的增量同步）

### 三个关键概念

| 概念 | 含义 |
| --- | --- |
| run_id（复制 ID） | 每个 Redis 实例启动时生成的 40 位随机字符串，标识它这一次"生命期"。从节点重连时用它判断主节点是不是换过一个了 |
| 复制偏移量 offset | 主节点每发出 N 字节写命令就累加自己的 offset，从节点每收到也累加。双方 offset 一致，说明数据一致 |
| 复制积压缓冲区 backlog | 主节点维护的一个固定大小的环形缓冲区（由 `repl-backlog-size` 控制，默认 1MB），保存最近发出去的写命令，用来支持断线后只补差量 |

### 全量复制是怎么走的

从节点在配置里写上 `replicaof`（旧版本叫 `slaveof`）之后：

1. 从节点主动连接主节点，先发一个 PING 确认对方可用
2. 如果主节点设了密码，从节点用配置里的 `masterauth` 完成认证
3. 从节点发送 `REPLCONF listening-port <端口>`，告诉主节点自己的端口
4. 从节点发送 `PSYNC ? -1`，表示"我是第一次来，做全量同步"
5. 主节点回复 `FULLRESYNC <run_id> <offset>`，同时 fork 出一个子进程生成 RDB 快照
6. 生成快照的这段时间里，主节点新收到的写命令会暂存到复制缓冲区里
7. 主节点把 RDB 文件发送给从节点（配置 `repl-diskless-sync yes` 时可以走无盘复制，直接把数据写进 socket，省掉落盘再读取的开销）
8. 从节点收到 RDB 后，先清空自己原有的数据，再加载这份快照
9. 加载完成后，主节点把缓冲区里积攒的增量命令补发过去，双方 offset 对齐，数据就一致了

### 增量同步（部分重同步）

链路断开后重连时，从节点会带上自己记录的 `run_id` 和 `offset` 再发一次 `PSYNC`：

- 如果主节点的 run_id 没变，并且 offset 之后的数据还都在 backlog 里，主节点就回复 `+CONTINUE`，只把缺失的那一小段命令补发给从节点，代价很低
- 如果主节点重启过（run_id 变了），或者断开时间太久、缺的数据已经超出 backlog 的范围，就只能重新做一次全量复制

所以把 `repl-backlog-size` 调大，能提高"断线重连只需增量同步"的概率。

### 心跳与超时

- 主节点默认每 10 秒向从节点发一次 PING，由 `repl-ping-replica-period` 控制
- 从节点默认每秒向主节点回一个 `REPLCONF ACK <offset>`，汇报自己收到哪了
- 如果超过 `repl-timeout`（默认 60 秒）双方都没收到对方的消息，就判定连接断开
- 用 `INFO replication` 看到的 `master_link_status:up`，就是指这条链路是通的

### 几个实用结论

- 首次建立主从、或者断线太久导致 backlog 不够，都会触发全量复制，此时主节点要 fork 子进程并传输整份 RDB，内存和网络的开销都不小，尽量避开业务高峰
- 全量复制期间主节点默认不阻塞（由 fork 出的子进程干活），但 fork 的那一瞬间会有短暂卡顿，实例内存越大越明显
- 从节点默认是只读的（`replica-read-only yes`），也可以再挂一层从节点，形成级联复制，用来分担主节点的复制压力
- 既然是异步复制，主从之间就存在毫秒到秒级的延迟，从节点上可能读到旧数据，对一致性要求高的读请求不要全部丢给从节点

---

Redis 的主从复制是一种数据复制机制，它允许将一个 Redis 实例的数据同步到一个或多个从节点上。主从复制主要用于提高 Redis 的数据可用性和扩展性。当主节点发生故障时，从节点可以接管服务，保证系统的高可用性。此外，它还可以用于分担读写负载，主节点处理写操作，从节点处理读操作

## 主从复制的优点

1. **数据高可用**：通过从节点复制主节点的数据，可以实现冗余存储。如果主节点故障，系统可以快速切换到从节点。
2. **负载均衡**：通过从节点分担读操作，减轻主节点的压力，提高系统的吞吐量。
3. **数据备份**：从节点的数据可以作为主节点的备份，增加数据安全性。

## Redis 主从复制的工作原理

1. **主节点（Master）**：负责处理所有的写入请求，数据被写入到主节点内存中。
2. **从节点（Slave）**：会主动从主节点拉取数据，保持与主节点数据的一致性。从节点是只读的，不能处理写请求。
3. **复制过程**：
   - 从节点连接到主节点，主节点会将自己的数据传输给从节点。
   - 一旦主节点有新的数据变更（写操作），它会将变更的数据发送到所有从节点，从节点会立即同步并更新自己的数据

## 部署 Redis 主从复制的步骤

准备两台机器，一台机器为主，一台机器为从

### 一、安装 Redis

更新软件包列表：

```bash
yum update
```

安装 `epel-release` 仓库：

```bash
yum install epel-release
```

安装 Redis：

```bash
yum -y install redis
```

### 二、配置主节点

**1. 编辑主节点的配置文件**

打开 Redis 主节点的配置文件 `/etc/redis/redis.conf`（默认路径可能因安装方式而有所不同，默认配置文件位于 `/etc/redis/redis.conf` 或 `/etc/redis.conf`）

```bash
vim /etc/redis/redis.conf
```

修改 bind 和 protected-mode：确保 Redis 能够从外部访问（例如从从节点访问），将 `protected-mode` 设置为 `no`，并绑定主节点的 IP 地址。

```ini
bind 0.0.0.0          # 允许任何 IP 访问
protected-mode no     # 禁用保护模式
```

修改端口（可选）：默认 Redis 使用 6379 端口，如果没有特殊需求，可以不修改。否则，修改为自己需要的端口

**2. 重启 Redis 主节点**

保存配置文件后，重启 Redis 主节点服务，使配置生效

**3. 检查主节点状态**

确保主节点正常运行，使用 `INFO replication` 命令查看主节点状态。

```bash
redis-cli INFO replication
```

返回信息中，`role` 应为 `master`，表示当前是主节点

### 三、配置从节点

**1. 编辑从节点的配置文件**

在从节点上，打开 Redis 配置文件 `/etc/redis/redis.conf`

```bash
vim /etc/redis/redis.conf
```

设置主节点：在从节点的配置文件中，添加以下配置，指定主节点的 IP 地址。

```ini
replicaof 172.22.4.3 6379      # Redis 5.0 版本以上使用
slaveof 172.22.4.3 6379        # Redis 5.0 版本以下使用
```

其中 `172.22.4.3` 是主节点的 IP 地址，`6379` 是主节点的 Redis 端口

禁用保护模式：与主节点类似，关闭保护模式，确保从节点可以接受外部连接。

```ini
protected-mode no
```

**2. 重启从节点 Redis**

配置完成后，重启 Redis 从节点服务，使配置生效。

```bash
systemctl restart redis-server
```

**3. 检查从节点状态**

在从节点上使用 `INFO replication` 命令查看状态，确保它连接到主节点

```bash
redis-cli INFO replication
```

返回信息中，`role` 应为 `slave`，`master_link_status` 应为 `up`，表示从节点正在成功连接到主节点

**4. 验证主从复制是否成功**

**5. 向主节点写入数据**

在主节点上，执行一些写入操作，例如设置一个键值对。

```bash
redis-cli -h 172.22.4.3 SET mykey "Hello, Redis!"
```

**6. 从从节点读取数据**

然后在从节点上读取数据，验证主从复制是否成功。

```bash
redis-cli -h 172.22.4.4 GET mykey
```

如果一切正常，返回的值应该是 `"Hello, Redis!"`

### 四、Redis 主从注意事项

**1. 数据同步延迟**

在高负载情况下，主节点和从节点之间可能存在数据同步延迟。如果要求实时性较高，可以考虑使用 Redis 集群。

**2. 读写分离**

在实际应用中，可以将主节点用于写操作，从节点用于读操作，达到读写分离，提升性能。

**3. 持久化配置**

默认情况下，Redis 主从复制不会持久化从节点的数据。你可以根据需要在从节点上配置持久化机制（如 RDB 快照或 AOF 日志）来确保数据安全。
