# MySQL 与 Redis 主从复制：相同与不同

## 一句话总览

两者的**目标完全一样**：都是"一主多从"，都是为了数据冗余、读扩展和故障热备，都靠异步复制做到最终一致。

但**实现思路完全不同**：

- MySQL 是**日志复制**——主库把数据变更记成磁盘日志（binlog），从库拉过来再重放一遍。
- Redis 是**数据集复制**——主库直接把内存里的数据和后续命令流推给从库。

---

## 一、原理上的相同点

| 相同点 | 说明 |
| --- | --- |
| 都是主从架构 | 写操作只允许在主节点进行，从节点承担读或热备 |
| 都是"记录变更 → 从库拉取 → 从库重放"三段式 | MySQL 是 binlog → relay log → 重放，Redis 是命令流 → 从节点执行 |
| 都是异步复制、最终一致 | 主节点不等从节点确认就返回客户端，因此可能丢最后一段数据、存在延迟 |
| 从节点默认只读 | 防止误写在从库上造成主从数据不一致 |
| 都支持一主多从和级联复制 | 从节点可以再挂下级从节点，分摊主节点的复制压力 |
| 都用"位点"来判断进度 | MySQL 靠 binlog file + position 或 GTID，Redis 靠 run_id + offset |
| 都存在"全量初始化"阶段 | 新从节点接入时要先拿到一份全量数据，之后才转入增量 |
| 都不自带自动故障转移 | 主节点挂了都需要额外组件接管（MySQL 靠 MHA、Orchestrator、MGR，Redis 靠 Sentinel 或 Cluster） |

---

## 二、原理上的不同点

| 维度 | MySQL | Redis |
| --- | --- | --- |
| 变更载体 | binlog，是**持久化到磁盘的日志文件** | 内存中的命令流，配合 RDB 全量快照 |
| 是否需要预先配置 | 需要，必须开启 `log-bin`、设置唯一的 `server-id`，还要选 binlog 格式 | 几乎开箱即用，写一行 `replicaof` 即可 |
| 实例标识 | 手工配置的 `server-id` | 自动生成的 `run_id`，无需人工分配 |
| 从节点的中转文件 | 必须落盘成 relay log，再读取重放（两段式落盘） | 没有 relay log，收到就直接在内存执行 |
| 线程模型 | 从库分 I/O 线程（拉日志）和 SQL 线程（重放），职责分离 | 从节点一条复制连接，命令执行仍是单线程 |
| 并行能力 | 支持并行复制（多 worker 线程），可缓解重放延迟 | 命令执行本身是单线程，不存在多线程重放 |
| 复制粒度 | 事务级、行级（`binlog_format=ROW`） | 命令级，一条写命令一条一条传 |
| 断点续传的凭据 | binlog 文件名 + 位点，或 GTID | run_id + offset，配合 `repl-backlog-size` 定义的积压缓冲区 |
| 全量同步方式 | 用 mysqldump / XtraBackup 导出，再 `CHANGE REPLICATION SOURCE` 建立关系 | 主节点 fork 子进程生成 RDB，直接推给从节点（可配无盘复制） |
| 全量同步对主节点的开销 | 主要压在磁盘 IO 和导出进程上 | fork 引发 copy-on-write，**内存占用可能瞬时接近翻倍** |
| 延迟量级 | 秒级到分钟级，大事务、DDL、单线程重放都会放大 | 通常毫秒级，因为是内存操作 |
| 延迟的查看指标 | `SHOW REPLICA STATUS` 里的 `Seconds_Behind_Source` | `INFO replication` 里主从的 offset 差值 |
| 是否有同步/半同步选项 | 有，半同步复制可等从库确认后再提交；组复制能提供更强一致 | 有 `WAIT numreplicas timeout`，可让客户端等待若干从节点确认；`min-replicas-to-write` 也能限制写入条件 |
| 拓扑灵活性 | 很灵活，支持双主、环形、多源复制（一个从库从多个主库拉） | 严格单向，一个从节点只能有一个主节点 |
| 能否只复制部分数据 | 能，用复制过滤器按库或表筛选 | 不能，复制的是整个数据集 |
| 与持久化的关系 | binlog 本身就是恢复与复制的共同基础，两者天然绑定 | 复制和持久化是两条独立链路，RDB/AOF 负责落盘，复制负责同步 |
| 从库能否写入 | 技术上能（`read_only` 可开可关），但会造成不一致 | 默认严格禁止，`replica-read-only yes` |

一句话记住这个差别：**MySQL 复制的是"操作日志"，Redis 复制的是"数据本身及其变更"。**

---

## 三、应用场景上的相同点

| 场景 | 说明 |
| --- | --- |
| 读写分离 | 主节点写、从节点读，提升整体吞吐 |
| 数据热备与故障切换 | 主节点故障时切换到从节点，缩短不可用时间 |
| 分摊查询压力 | 多个从节点分散高并发读请求 |
| 在从节点执行重活 | MySQL 在从库跑统计查询、跑备份；Redis 在从节点做持久化落盘，都避免影响主节点 |
| 都要容忍延迟 | 两者都要面对"从节点数据可能落后"，写入后立即读的场景要走主节点 |
| 都需要额外组件做自动切换 | 主从本身只解决冗余，不解决自动接管 |

---

## 四、应用场景上的不同点

### MySQL 特有的用法

- **脱机备份**：在从库上做全量备份，不影响主库对外服务
- **报表与数据分析**：把耗时的聚合查询放到从库执行
- **异地容灾**：跨机房部署从库，主节点所在地故障后仍有可用副本
- **版本升级灰度**：先升级从库验证新版本，再切换
- **延迟从库**：刻意让从库落后主库若干小时，用于误删数据后的快速回滚（`SOURCE_DELAY`）
- **跨版本、跨云迁移**：用主从关系把数据平滑搬到新环境
- **只复制部分库表**：多业务共用实例时，按库或表筛选复制范围
- **数据校验**：用从库与主库做一致性比对

### Redis 特有的用法

- **把持久化下沉到从节点**：主节点关闭 RDB 和 AOF 换取性能，由从节点负责落盘，这是很常见的优化手法
- **缓存场景的高可用**：Redis 多用于缓存，从节点主要保证缓存服务不中断
- **从节点断链仍可服务**：链路断开时默认继续用旧数据对外提供服务（`replica-serve-stale-data`），可用性优先，但可能读到过期数据
- **粒度上受限**：不能"只复制一部分数据"，也不适合做主从之间的数据比对

### 对延迟的敏感度不同

MySQL 的复制延迟可能是分钟级，所以业务上要专门设计（强制走主库、判断延迟、串行化要求高的查询不打到从库）。

Redis 的复制延迟通常只有毫秒级，读从节点的风险小得多，但对一致性要求极高的场景仍不建议读从节点。

## 五、两者都成立的三条前提

**第一，异步复制意味着可能丢数据。** 主节点在把变更发出去之前就回复了客户端，所以主节点突然断电时最后几条写入会丢。想缓解，MySQL 可以开半同步复制，Redis 可以配 `min-replicas-to-write`。

**第二，主从不等于高可用。** 两者都只提供了副本，没有提供自动切换。MySQL 要配 MHA、Orchestrator 或 MGR，Redis 要配 Sentinel 或 Cluster。

**第三，副本不等于备份。** 误执行的 `DELETE`、`DROP`、`FLUSHALL` 会瞬间同步到所有节点，副本救不了你。备份必须独立做，这一层不能省。
