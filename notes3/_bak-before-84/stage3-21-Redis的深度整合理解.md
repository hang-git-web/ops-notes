# 为什么 Redis 需要哨兵、Cluster 和持久化，而 MySQL 主从配置里没有

## 这篇文章解决什么问题

已经理解了主从复制之后，自然会产生一个疑问：

> **为什么 Redis 做了主从复制之后，还需要哨兵模式部署、Cluster 集群部署，以及持久化？**
>
> **为什么 MySQL 的主从配置里看不到这些东西，而 Redis 里必须有？**
>
> **分别是在什么场景下需要？**

本文就是回答这个问题。核心结论一句话：

> **Redis 是内存数据库，MySQL 是磁盘数据库。数据在哪、谁是权威副本，决定了两边所有的设计差异。**

MySQL 并不是"不需要"这三样东西，而是它们由别的部件承担了，或者被拆分到了另外的文档里。

---

## 一、先把对应关系对上

| 需求 | Redis 的解决方式 | MySQL 里的对应物 | 为什么看起来 MySQL 不需要 |
| --- | --- | --- | --- |
| 持久化（重启不丢） | RDB 快照 / AOF 日志，**必须显式开启** | InnoDB 数据文件 + redo log，**默认就在做** | MySQL 数据本来就落盘，持久化是默认行为 |
| 故障自动切换 | Sentinel（或 Cluster 内置） | MHA、Orchestrator、MGR、云 RDS 高可用版 | MySQL 主从**也没有**自动切换，只是这些组件不写在主从配置里 |
| 水平扩容 / 分片 | Cluster（16384 个哈希槽） | 分库分表中间件（ShardingSphere、Vitess、MyCat） | MySQL 靠加磁盘、加内存能撑很久，分片通常更晚才需要，而且是另一个话题 |

这里最关键的一条是：**MySQL 主从复制同样不能自动切换**。在 MySQL 主从的笔记里看不到 MHA、Orchestrator，是因为它们属于"高可用方案"那一章，不属于"主从配置"那一章。

所以准确的问法不是"为什么 MySQL 不需要"，而是：**为什么 Redis 把这些能力做进了自己的生态，而 MySQL 把它们留给了第三方组件。**

---

## 二、逐条回答"为什么 MySQL 主从配置里没有"

### 1. 持久化：MySQL 默认就在做，Redis 必须显式开启

MySQL 里，**磁盘是权威**，内存（buffer pool）只是缓存。数据写进来先写日志再刷盘，进程挂了重启，数据还在，最多丢掉还没落盘的极小一部分，而 redo log 会把这部分补上。所以"持久化"这件事，MySQL 从设计上就做好了，你不需要为它做任何决定。

Redis 反过来，**内存是权威**，磁盘上的 RDB/AOF 只是副本。进程一停，内存就没了，数据就没了。所以持久化在 Redis 里是一道必须自己打开、而且要权衡的开关：

| 方式 | 特点 | 代价 |
| --- | --- | --- |
| RDB 快照 | 性能好、文件小、恢复快 | 可能丢最后几分钟的数据 |
| AOF 日志 | 丢得少、更安全 | 文件大、写入开销高 |

这是纯粹的取舍，没有默认答案。

### 2. 自动故障转移：MySQL 也没有，只是交给了别的组件

Redis 的哨兵做三件事：检测主节点故障、选出新主、通知客户端新地址。这三件事 MySQL 主从一样需要，只是解法不同：

| 环节 | Redis | MySQL |
| --- | --- | --- |
| 故障检测 | 多个哨兵投票（主观下线 → 客观下线） | MHA / Orchestrator / MGR / 云 RDS |
| 选新主 | 哨兵按优先级、复制偏移量挑选 | 同上 |
| 客户端寻址 | 客户端向哨兵查询"当前主是谁" | 常见做法是 VIP 或代理中间件，应用连虚拟地址，切换时改网络指向 |

Redis 客户端普遍原生支持 Sentinel 协议，向哨兵问一次就知道新主在哪，切换后自动重连；MySQL 则倾向于在网络层解决（VIP、中间件），应用无感知。两种思路各有取舍，但需求本身是一样的。

### 3. 分片扩容：MySQL 更晚才需要，而且属于另一个话题

MySQL 单个实例做到 TB 级很常见，磁盘不够加磁盘，内存不够加内存，成本相对线性。真到了撑不住的时候，分库分表在应用层和中间件层解决，数据库本身不需要变。

Redis 的数据集**必须整个装进内存**，而内存是服务器上最贵、最不灵活的部件，一台机器几十到几百 GB 就到头了。撞上天花板后，也没有"加块硬盘"这种便宜的解法，**只能在数据库层把数据拆开**。这就是 Cluster 存在的全部理由。

所以两者的发生时机不同：MySQL 的分片是业务长到中后期才考虑的事，Redis 的分片往往数据量稍微一大就成了必答题。

## 三、背后的三个根本原因

### 原因一：权威副本在磁盘还是内存

这是所有差异的源头。

- **MySQL**：磁盘是权威，内存是缓存。所以持久化是"默认行为"，你甚至不会意识到它的存在。
- **Redis**：内存是权威，磁盘文件只是副本。所以持久化是"必须显式打开并权衡的开关"。

这也解释了为什么 Redis 的持久化和复制是**两件独立的事**，缺一不可。

#### 一个经典事故：为什么复制替代不了持久化

> 主节点关闭了持久化，只靠从节点。某天主节点重启，内存是空的，于是它以一个"空数据集"的身份上线。从节点检测到主节点回来了，做全量同步——**把主节点那份空数据复制了过来**，从节点的数据被清空。整套数据就这么没了。

原因是复制同步的是"内存状态"，主节点内存为空，从节点就跟着变空。

结论：**复制防的是进程崩溃，持久化防的是整机重启、断电，以及数据被同步成空。**

### 原因二：容量天花板的高度不同

| | MySQL | Redis |
| --- | --- | --- |
| 数据放哪 | 磁盘，可到 TB 级 | 内存，几十到几百 GB |
| 扩容方式 | 加磁盘、加内存，成本线性 | 内存最贵，加不动 |
| 撑不住怎么办 | 分库分表（应用层/中间件层） | 只能在数据库层分片 → Cluster |

### 原因三：停机代价不同，自动切换的紧迫性不同

Redis 通常站在**最前面**——缓存、会话、排行榜、消息队列。它一旦不可用，后面的数据库会被瞬间打穿（缓存击穿、雪崩），用户直接看到报错。也就是说 Redis 停机的影响是**立刻且全局**的。

MySQL 在架构里通常更靠后，主库短暂不可用，应用可能先降级、先排队、先报错重试，影响力相对可控一点。

再加上 Redis 本身很轻，多跑一个哨兵进程成本极低（哨兵不存数据，只做监控和选举），社区自然就把"故障检测 + 选主 + 通知客户端"做成了内置生态。

## 四、场景决策表

| 场景 | Redis 该怎么配 |
| --- | --- |
| 本地学习、开发环境 | 单机就够，持久化可关 |
| 纯缓存，数据丢了能从数据库重建 | 单机或主从 + 哨兵，持久化可关或只留 RDB |
| 存会话、购物车、分布式锁这类不能丢的数据 | 主从 + 哨兵 + **必须开 AOF** |
| 排行榜、计数器，允许极端情况下丢一点 | 主从 + 哨兵，RDB 即可 |
| 数据量超过单机内存 | 必须上 Cluster |
| 写入并发很高，单个主节点扛不住 | 必须上 Cluster |
| 要求机房级容灾 | Cluster 跨机房部署，或主从 + 哨兵异地部署 |

对应的 MySQL 侧则是：小规模主从就够用；要求自动切换就加 MHA / Orchestrator / MGR；数据量爆炸就上分库分表中间件。

---

## 五、一句话总结

**MySQL 的主从配置里没有持久化、没有自动切换、没有分片，是因为持久化它默认就有，自动切换和分片它交给了别的组件；而 Redis 因为用内存当权威、容量受限于内存、又站在流量最前线，这三件事全部变成了必须在 Redis 自己这一层解决的问题。**

换个说法：**MySQL 是"磁盘数据库附带了一份内存缓存"，Redis 是"内存数据库附加了两套磁盘副本（持久化文件 + 从节点）"。** 位置颠倒了，所以需要的补丁也就颠倒了。
