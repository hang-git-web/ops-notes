# 故障排查方法论:先分层,再验证

> 排障能力 = 知道请求经过哪些层 + 知道每层用什么工具观测 + 用证据验证假设。
> 工具可以记不住,思路必须清楚。

---

## 一、本质:排障就是沿请求路径缩小范围

一次访问要穿过很多层,任何一层断了,用户看到的都是同一句话:“网站打不开”。

```text
客户端 → DNS → 网络链路 → 端口/防火墙 → 服务进程 → 应用代码 → 依赖(DB/缓存)
```

所以排障不是“找 bug”,而是**先确定是哪一层断的,再在该层内定位具体原因**。每层都有自己的“观测窗口”:

| 层 | 观测手段 | 能看到什么 |
| --- | --- | --- |
| 客户端/DNS | `nslookup`、换网络、清缓存 | 域名解析、本地环境问题 |
| 网络链路 | `ping`、`traceroute`、`nc -vz` | 能否到达、是否被拦截 |
| 端口/防火墙 | `ss -nltp`、`iptables -nL`、云安全组 | 服务是否在监听、是否被拦 |
| 系统资源 | `top`、`free`、`df`、`vmstat` | CPU/内存/磁盘/IO 瓶颈 |
| 应用 | `systemctl status`、应用日志、`nginx -t` | 服务状态、报错、配置错误 |
| 依赖 | 后端端口、数据库日志 | 连接失败、慢查询、锁 |

## 二、工具选择:先证据,后抓包

判断标准只有一条:**这次故障有没有留下痕迹?**

```text
有痕迹(日志/指标/状态) → 分析痕迹
无痕迹(服务端什么都不知道) → 抓包确认请求是否到达
```

| 场景 | 用什么 | 为什么 |
| --- | --- | --- |
| 访问变慢、CPU 高 | `top` + 日志聚合 | 数据直接指向资源或流量,成本最低 |
| 报 502 / 500 | 应用错误日志 + 后端端口 | 状态码本身就是“哪一层出的错”的线索 |
| 报 403 | `ls -lZ`、`getenforce` | 文件可读但被拒,典型是权限或 SELinux |
| 报 404 | `nginx -t`、核对 root | 路径或配置问题 |
| 服务端日志完全空白 | `tcpdump` | 没有证据,必须制造证据 |
| 时好时坏 | 监控趋势 + 并发分析 | 偶发问题靠长时间数据,不是单次抓包 |

**一个必须建立的认知:网络可达 ≠ 服务可用。**
`ping` 通只说明 ICMP 通,不代表 TCP 端口能连、应用能响应。很多服务器还直接禁用了 ICMP。所以判断服务是否可用,要用 `nc -vz`、`curl -I` 这类针对业务端口的探测。

**为什么抓包放在最后**:它记录的是网卡上的原始数据,是网络与主机之间唯一的客观边界,不受“日志有没有开、记没记全”的影响。当应用说自己没收到请求时,只有抓包能证明这句话是真是假。它信息最真实,但成本最高、最难读,所以留到没有其他证据时再用。

## 三、现象 → 层次速查

| 现象 | 先怀疑 | 第一步 |
| --- | --- | --- |
| 完全打不开,日志空白 | 网络/链路 | 抓包看请求是否到达 |
| 502 | 后端服务/中间件 | `error.log` + 后端端口 |
| 403 | 权限/SELinux | `ls -lZ`、`getenforce` |
| 404 | 路径/配置 | `nginx -t`、核对 `root` |
| 500/空白 | 应用代码 | 命令行直接跑脚本看报错 |
| 访问慢 | 资源/恶意流量 | `top` + 日志聚合 |
| 偶发失败 | 并发/连接池/超时 | 看监控趋势与峰值 |

## 四、决策树

```text
故障
 │
 ├─ 有日志/指标/进程状态? ── 有 ──→ 直接分析证据 → 能定位就修
 │                                    └─ 定位不了 → 抓包
 │
 └─ 没有(服务端无任何记录) ──→ 抓包
                                    │
                    ┌───────────────┴───────────────┐
              抓不到包                         抓到包但无响应
        → 客户端/上游/云安全组              → 端口/防火墙/应用
```

## 五、两个案例:同一思路的两条分支

**案例一(新站点打不开)**
服务端一切正常但日志空白 → 没有证据 → 抓包 → 抓不到任何包 → 请求根本没到服务器 → 上游拦截(高危端口 6666 被云平台封禁)。

**案例二(生产站点变慢)**
服务活着、日志里有大量异常请求 → 有证据 → `top` + 日志聚合 → 某 IP 请求数万次 → 恶意刷访问 → 封禁。

两个案例工具不同,方法完全相同:**有证据先分析,没证据再抓包**。

## 六、常见误区

- 一上来就重启 —— 破坏现场,根因再也找不到
- 同时改多处配置 —— 无法归因
- 只看应用不看系统和网络 —— 跳层排查
- 忽略最近变更 —— 错过最快的线索
- 把“恢复业务”当成“解决问题” —— 故障必然复发
- 用 `ping` 判断服务是否可用 —— 混淆网络层与服务层

---

## 七、一句话总结

排障的本质:**沿请求路径分层缩小范围,用证据代替猜测,用单变量隔离原因,先恢复业务再追根因。**

当你能说清“我为什么用这个工具、它验证了什么假设”,排障就从经验变成了方法。
