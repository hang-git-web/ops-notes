# NFS 与 rsync 原理与作用对比(结合公司实际场景)

> 导语:两者都涉及"跨网络传文件",但解决的是**完全不同的问题**——
> **NFS 解决"多台机器怎么共用同一份数据",rsync 解决"怎么把数据复制到另一处"。**
> 把这两个问题混在一起,是生产事故的常见来源。

## 一、先记住结论

| 维度 | NFS | rsync |
| --- | --- | --- |
| 一句话 | **共享同一份数据** | **复制出一份副本** |
| 数据份数 | 1 份(在服务端) | 2 份及以上(每端各一份) |
| 是否实时 | 实时(每次读写都走网络) | 非实时(执行时才同步) |
| 典型动作 | `mount` 挂载后当本地目录用 | 执行一次命令,传完结束 |
| 公司里的角色 | 共享存储 | 备份 / 迁移 / 发布 |

## 二、NFS:网络文件系统(共享)

### 1. 原理

NFS 采用**客户端-服务端**模型,本质是"把远端的文件系统调用,通过网络转发到服务端去执行":

```text
应用程序
   ↓ 读写文件(open/read/write)
客户端内核 VFS
   ↓ NFS 客户端模块
   ↓ 网络(RPC 调用)
服务端 rpcbind / nfsd
   ↓
服务端本地文件系统(真正的磁盘)
```

关键点:

- **数据只有一份,存在服务端磁盘上**;客户端只是"能用",并不持有数据
- 服务端通过 `exportfs` 导出目录,客户端通过 `mount -t nfs` 挂载
- 权限沿用 Linux 的 **UID/GID 模型**,靠 `root_squash` / `no_root_squash` 控制 root 身份
- NFSv3 依赖 `rpcbind`(111 端口)和动态端口;NFSv4 只走 **2049** 一个端口,更利于防火墙配置

### 2. 作用与价值

| 价值 | 说明 |
| --- | --- |
| 集中存储 | 数据只存一份,省磁盘、省管理成本 |
| 实时一致 | 任何一台机器改了,其他机器立刻看到 |
| 便于扩容 | 加一台应用服务器,挂载一下就能用 |
| 集中备份 | 只需备份服务端一份数据,不用逐台备份 |

### 3. 公司里的典型场景

| 场景 | 说明 |
| --- | --- |
| 电商网站多台 Web 共享商品图片 | 用户上传的图片必须所有节点都能读 |
| 应用集群共享配置文件 | 改一次,所有节点生效 |
| K8s / 容器平台的持久化卷(PV) | 多个 Pod 挂载同一个目录 |
| 备份服务器的存储目录 | 业务机直接把备份写进共享目录 |
| 渲染 / 计算集群共享素材库 | 几十台机器读同一批大文件 |
| 日志集中目录 | 多台机器往同一个目录写日志 |

### 4. 风险与限制

| 风险 | 说明 | 缓解手段 |
| --- | --- | --- |
| **单点故障** | NFS 服务端挂了,所有客户端都不可用 | DRBD + Keepalived 双机热备 |
| **不是备份** | 数据只有一份,误删/勒索病毒会波及全部 | 必须再做 rsync 异地备份 |
| 断网时挂载点卡死 | 默认 `hard` 挂载会一直重试 | 用 `soft` + `timeo` 或挂载 `autofs` |
| 性能受网络影响 | 高频小文件读写延迟明显 | 大文件为主;或换分布式存储 |
| 权限模型依赖 UID | 两端 UID 不一致会导致权限错乱 | 统一 UID,或用 `all_squash` + `anonuid` |

## 三、rsync:远程增量同步(复制)

### 1. 原理

rsync 的核心价值在**"只传变化的部分"**,靠的是它自己的差分算法:

```text
1. 双方先交换文件列表(大小、mtime)
2. 对目标端文件分块计算滚动校验和与强校验和(MD5)
3. 源端对本地文件滑动计算校验和,找出相同的块
4. 只把"匹配不上的块 + 新块"传过去
5. 目标端用收到的块 + 本地已有块,拼出新文件
```

所以它的传输量取决于**文件变化量**,而不是文件总大小——这就是它比 `scp`/`cp` 高效的根本原因。

其他关键机制:

| 机制 | 参数 | 作用 |
| --- | --- | --- |
| 压缩传输 | `-z` | 省带宽 |
| 保留属性 | `-a` | 权限、时间、软链接等 |
| 断点续传 | `--partial` / `--append` | 大文件中断后接着传 |
| 限速 | `--bwlimit=10000` | 避免占满生产带宽 |
| 删除目标多余文件 | `--delete` | 保持两端完全一致(**危险**) |
| 排除规则 | `--exclude` | 跳过缓存、临时文件 |

两种连接方式:

| 方式 | 写法 | 特点 |
| --- | --- | --- |
| over SSH | `user@host:/path` | 走 22 端口,免密密钥认证 |
| daemon 模式 | `user@host::模块名` | 走 873 端口,模块化 + 口令文件认证 |

### 2. 作用与价值

| 价值 | 说明 |
| --- | --- |
| 省时间省带宽 | 增量传输,大目录重复同步几乎秒完成 |
| 保留副本 | 天然是"另一份数据",可跨机器、跨机房 |
| 可按天留版本 | 目标端用 `$(date +%Y%m%d)` 建目录 |
| 易自动化 | 配合 cron / 脚本 / Ansible 批量执行 |
| 支持校验 | `-c` 按校验和比较,能发现内容变化 |

### 3. 公司里的典型场景

| 场景 | 说明 |
| --- | --- |
| 数据库备份推送 | mysqldump 导出后 rsync 到备份机(你已有实践) |
| 网站代码发布 | 从构建机推送到多台应用服务器 |
| 数据迁移 / 上云 | 首次全量 + 后续增量,可断点续传 |
| 异地容灾 | 跨机房、跨地域增量复制 |
| 文件归档 | 按日期目录保存历史版本 |
| 配合监控 | 同步失败触发 Zabbix 告警 |

### 4. 风险与限制

| 风险 | 说明 |
| --- | --- |
| **非实时** | 靠 cron 或触发机制,存在同步延迟 |
| **不能当共享** | 两端各一份,多端同时写会互相覆盖 |
| `--delete` 危险 | 源端为空时会把备份端清空 |
| 口令文件权限 | 必须 600,否则报 `password file must not be other-accessible` |
| 首次全量慢 | 第一次同步等于全量复制,要评估窗口 |
| cron 环境差异 | cron 里没有登录环境变量,脚本要用绝对路径 |

## 四、核心对比表

| 对比项 | NFS | rsync |
| --- | --- | --- |
| 定位 | 网络文件系统(协议) | 文件同步工具(命令) |
| 数据份数 | 1 份 | 2 份及以上 |
| 访问方式 | 挂载后像本地目录 | 执行一次命令 |
| 实时性 | 实时 | 定时 / 触发式 |
| 通信端口 | 2049(+111) | 873(daemon)或 22(ssh) |
| 传输机制 | 文件系统调用转发 | 差分算法,只传变化块 |
| 断开影响 | 客户端访问卡死/失败 | 传输中断,重跑即可续传 |
| 权限模型 | 服务端 UID/GID 映射 | 不涉及,只是复制文件 |
| 读写并发 | 支持多客户端同时读写 | 不适合多端同时写 |
| 典型角色 | 共享存储 | 备份 / 迁移 / 发布 |
| 运维复杂度 | 中(要处理单点、权限、防火墙) | 低(一个命令 + 定时任务) |
| 能否替代对方 | 不能替代备份 | 不能替代共享 |

## 五、结合公司实际场景的选型

| 业务需求 | 选择 | 理由 |
| --- | --- | --- |
| 电商网站 6 台 Web 共享用户上传的图片 | **NFS** | 数据必须唯一且实时一致 |
| 每天凌晨把订单库备份送到备份机 | **rsync** | 要的是副本,而且希望增量省时间 |
| 把新版本代码发布到 10 台应用服务器 | **rsync** | 各节点保留自己的副本,推送完就结束 |
| 容器平台多个 Pod 挂载同一上传目录 | **NFS**(或 Ceph) | 多实例共享同一份数据 |
| 两地机房做数据容灾 | **rsync** | 跨广域网增量传输最划算 |
| 应用集群共享一份配置文件 | **NFS** | 改一次全局生效 |
| 需要保留每天的数据快照 | **rsync** | 目标端按日期建目录,天然留版本 |
| 要求业务不中断、服务端故障自动切换 | **NFS + DRBD + Keepalived** | NFS 保证共享,DRBD 保证数据,Keepalived 保证切换 |

## 六、两者结合的经典架构(推荐)

```text
              ┌────────────── 应用层 ──────────────┐
              │  Web1    Web2    Web3   ...        │
              └───────┬───────┬───────┬────────────┘
                      │ NFS 协议(共享同一份数据)
                      ↓
              ┌──────────────────────────────┐
              │   NAS / NFS 服务端            │
              │   /data/uploads  /data/config │
              └──────────────┬───────────────┘
                             │ rsync(定时/触发,增量复制)
                             ↓
              ┌──────────────────────────────┐
              │   备份服务器 / 异地机房        │
              │   按日期目录归档 + 保留策略     │
              └──────────────────────────────┘
                             │
                             ↓
                    Zabbix 监控同步状态 → 邮件/企业微信告警
```

**这段架构解决了两件事**:

1. `NFS` 让多台应用服务器**共用同一份在线数据**(解决"一致性")
2. `rsync` 把这份数据**复制到另一处**(解决"防丢失")

一句话:**NFS 保业务连续,rsync 保数据不丢,两者缺一不可。**

## 七、实操:两边各一个最小案例

### 7.1 NFS 共享(服务端 + 客户端)

**服务端**

```bash
# 1. 安装
yum install -y nfs-utils rpcbind

# 2. 导出目录
mkdir -p /data/share && echo "hello nfs" > /data/share/test.txt
cat >>/etc/exports <<'EOF'
/data/share 192.168.1.0/24(rw,sync,no_root_squash)
EOF

# 3. 启动并验证
systemctl enable --now rpcbind nfs-server
exportfs -v
showmount -e localhost
```

**客户端**

```bash
yum install -y nfs-utils
mkdir -p /mnt/nfs
mount -t nfs 192.168.1.10:/data/share /mnt/nfs

# 验证:看到服务端的文件即成功
ls -l /mnt/nfs
cat /mnt/nfs/test.txt

# 开机自动挂载
echo "192.168.1.10:/data/share /mnt/nfs nfs defaults,_netdev 0 0" >>/etc/fstab
```

**检验要点**:客户端写入文件后,服务端 `/data/share` 立刻能看到(证明是"同一份数据")。

### 7.2 rsync 备份(服务端模块 + 客户端推送)

**服务端**

```bash
yum install -y rsync
mkdir -p /data/rsync_mysql

cat >/etc/rsyncd.conf <<'EOF'
uid = root
gid = root
use chroot = no
read only = no
hosts allow = 192.168.0.0/255.255.0.0
secrets file = /etc/rsyncd/rsyncd.passwd
log file = /var/log/rsync.log
transfer logging = yes
timeout = 300

[MySQL_backup]
path = /data/rsync_mysql/
read only = no
auth users = mysql
list = yes
EOF

# 口令文件:格式为 用户名:密码,权限必须 600
mkdir -p /etc/rsyncd
PASSWD=$(openssl rand -base64 12 | tr -d '/|+=')
echo "mysql:${PASSWD}" >/etc/rsyncd/rsyncd.passwd
chmod 600 /etc/rsyncd/rsyncd.passwd
echo "口令是:${PASSWD}"      # 记下来,客户端要用

systemctl enable --now rsyncd
ss -tlnp | grep 873
```

**客户端**

```bash
yum install -y rsync
mkdir -p /shell /data/mysqlbackup

# 口令文件:只写密码,权限必须 600
echo "把上面记下的口令填这里" >/shell/mysqlpasswd.log
chmod 600 /shell/mysqlpasswd.log

# 推送
rsync -avz /data/mysqlbackup mysql@192.168.1.10::MySQL_backup \
  --password-file=/shell/mysqlpasswd.log
```

**检验要点**:服务端 `/data/rsync_mysql/` 出现文件,客户端再改一个文件重新同步,观察 rsync 只传变化部分。

## 八、高频坑清单

### NFS 侧

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 客户端 `mount` 超时 | 防火墙没放行 2049/111 | 放行端口;优先用 NFSv4,只需 2049 |
| 权限错乱、写入失败 | 两端 UID/GID 不一致或 root_squash | 统一 UID,或配置 `all_squash` + `anonuid` |
| 服务端故障,客户端卡死 | 单点 + `hard` 挂载 | 双机热备;客户端用 `soft`、`autofs` |
| 服务端数据被误删 | 以为 NFS 就是备份 | **NFS ≠ 备份**,必须配 rsync 异地备份 |

### rsync 侧

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `@ERROR: Unknown module` | 模块名大小写不一致 | 两边名称严格一致(rsync 区分大小写) |
| `@ERROR: module is read only` | 服务端模块 `read only = yes` | 推送数据必须设为 `no` |
| `password file must not be other-accessible` | 口令文件权限不是 600 | `chmod 600` |
| `auth failed` | 服务端密码文件格式错 | 服务端 `用户名:密码`,客户端**只写密码** |
| 备份端被清空 | 用了 `--delete` 且源目录为空 | 加 `--dry-run` 预览,或 `--backup --backup-dir` 保留被删文件 |

### 最容易踩的一个:源路径结尾的斜杠

```bash
rsync -avz /data/mysqlbackup  /backup/     # 结果:/backup/mysqlbackup/...
rsync -avz /data/mysqlbackup/ /backup/     # 结果:/backup/...(内容直接放进去)
```

**带斜杠 = 同步"目录里的内容";不带斜杠 = 把"目录本身"同步过去。** 这个差异导致的备份目录结构错误非常常见。

## 九、一页速查

```text
多台机器要读写同一份数据  → NFS(共享,数据一份)
要把数据复制到别处保存    → rsync(备份,数据多份)
要求故障自动切换          → NFS + DRBD + Keepalived
要求数据不丢              → 在 NFS 之上再加 rsync 异地备份
```

| 记忆口诀 | |
| --- | --- |
| NFS | 一份数据,多方共享,实时一致 |
| rsync | 多份副本,定时复制,只传变化 |
| 组合 | NFS 保业务,rsync 保数据 |
